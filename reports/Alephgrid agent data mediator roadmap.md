# Federate the connection, materialize the answer

Alephgrid should become a thin, governed broker over DuckDB's own connector ecosystem — not a connector framework of its own — and it should resolve the federation-vs-ingest debate with a split verdict: **federation-first for connectivity** (ATTACH sources live, keep DuckDB as the single planner) and **ingest-shaped for serving** (every result the grid or an agent touches is materialized into local, revision-stamped DuckDB storage by default). The evidence is consistent across both research passes: DuckDB's scanner ecosystem now covers Postgres/MySQL/SQLite with read-write ATTACH, Iceberg writes (since 1.4.0), and Delta/Unity Catalog writes (since May 2026) ([DuckDB lakehouse formats](https://duckdb.org/docs/lts/lakehouse_formats.html); [Delta/UC blog](https://duckdb.org/2026/05/07/delta-uc-updates.html)), so the universal-connectivity goal is reachable by orchestrating extensions plus an ADBC fallback for warehouses — while GlareDB's abandoned attempt to build its own connector fleet shows why Alephgrid should not ([GlareDB repo](https://github.com/GlareDB/glaredb)). On the agent side, the field has converged on exactly the harness Alephgrid already sketched in its earlier trusted-agent research: a three-tier tool surface (metric registry → constrained SQL → audited raw SQL), curated context served through search rather than preloaded, and token-bounded previews with opaque result handles — dbt's benchmark measured **98–100% accuracy for semantic-layer queries vs 84–90% for text-to-SQL** on the same questions ([dbt 2026 benchmark](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)), and Spider 2.0's DuckDB/dbt split still tops out at **65.6%** for free-form agents ([spider2-sql.github.io](https://spider2-sql.github.io/)). The competitive window is open: Quadratic, the only open-source AI-native spreadsheet of note, went closed-source in March 2026 and its repo now 404s ([Quadratic blog](https://www.quadratichq.com/blog/comparing-the-5-best-open-source-spreadsheets)), leaving no self-hosted, open, governed agent-data mediator in the market. The roadmap below sequences identity → read-only agent gateway → connector broker → materialization/cache tier → semantic registry → public evals, folding in the earlier research's settled conclusions (governed-workspace positioning, Cedar-then-MCP sequencing, answer receipts, proposal-first mutations) as the foundation everything else stands on.

## Universal connectivity means brokering DuckDB's connectors, not building new ones

The strategic lesson of the connectivity research is negative space: GlareDB built almost exactly the proposed broker — a Rust engine (DataFusion) with Postgres/BigQuery/Snowflake external tables and MotherDuck-style hybrid execution — then threw the engine away for a rewrite, "temporarily removed" external-system support, and is now described by third parties as pivoted or abandoned ([GlareDB GitHub](https://github.com/GlareDB/glaredb); [dbdb.io](https://dbdb.io/db/glaredb)). Maintaining N native connectors on a general-purpose engine is a treadmill a small OSS team cannot run. The defensible position is to let DuckDB Labs run it: the 2022→2026 trendline shows Postgres filter pushdown going from default-off experimental to default-on with a remote-pushdown optimizer that ships whole queries to the source ([DuckDB Postgres extension docs](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html)), Iceberg gaining full read/write catalog ATTACH against Polaris, Lakekeeper, Glue, R2 and S3 Tables ([DuckDB Iceberg catalogs](https://duckdb.org/docs/current/core_extensions/iceberg/catalogs.html)), and Delta/Unity Catalog shedding experimental status with writes and time travel ([DuckDB blog](https://duckdb.org/2026/05/07/delta-uc-updates.html)). Alephgrid's connectivity layer should therefore be a **credential-holding, policy-enforcing, caching orchestrator over ATTACH**, roughly three tiers: Tier 1, core-signed DuckDB extensions enabled by default (postgres, mysql, sqlite, httpfs/S3, iceberg, delta, excel); Tier 2, community extensions (gsheets, nanodbc/ODBC) opt-in per deployment and ideally behind a worker-process boundary, because DuckDB's own operations manual says a web service executing untrusted user SQL should disable community extensions ([Securing Extensions](https://duckdb.org/docs/current/operations_manual/securing_duckdb/securing_extensions.html)); Tier 3, **ADBC as the fallback for warehouses DuckDB cannot scan natively** (Snowflake, BigQuery, Databricks SQL), consumed from Rust via the ADBC driver manager loading foreign shared-library drivers ([apache/arrow-adbc](https://github.com/apache/arrow-adbc)) — with the caveat that ADBC executes whole statements and provides no pushdown layer, so the broker composes source-dialect SQL itself.

The security design of this broker is dictated by one of the clearest evidence trails in the notes: Metabase's multi-year CVE record proves that **the user-supplied connection string is the most dangerous input a mediator accepts**. CVE-2023-38646 chained an H2 connection string into pre-auth RCE ([Assetnote writeup](https://www.assetnote.io/resources/research/chaining-our-way-to-pre-auth-rce-in-metabase-cve-2023-38646)); CVE-2026-50147 turned user-settable JDBC parameters into arbitrary file reads ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-50147/)); 2026 advisories add RCE via Snowflake connection config and a validation-bypass re-opening the original H2 hole ([Metabase CVE tracker](https://www.cvelogic.com/vendor/metabase)). The counter-model is Cube's: credentials are deployment config held server-side, and clients authenticate with tokens that never carry database secrets ([Cube configuration docs](https://docs.cube.dev/configuration/overview)). Concretely: connections are server-side rows built from **structured, per-driver-allowlisted fields — never raw URIs or free-form parameter maps**; agents and clients reference connections by opaque ID only; DuckDB secrets are created per-session in memory so nothing persists for `duckdb_secrets()` to leak; every ATTACH defaults to READ_ONLY with writes as an explicit, audited capability; SSRF controls (reject private/metadata IP ranges, pin DNS at connect time) guard user-supplied hosts; and OAuth-family sources (Sheets, BigQuery, Snowflake) get server-held refresh tokens minting short-lived access tokens injected into session-scoped secrets — which is exactly the shape the gsheets extension's `access_token` provider consumes ([DuckDB community extensions: gsheets](https://duckdb.org/community_extensions/extensions/gsheets)). This extends, rather than replaces, the earlier security research's conclusion that the embedded engine itself needs hardening (`enable_external_access=false`, locked configuration, no agent-reachable INSTALL or filesystem paths — controls Alephgrid's engine already partially enforces per its architecture docs).

## The federation-vs-ingest debate resolves into one architecture with two defaults

The two adversarial positions are both well-evidenced, and presenting them fairly matters because each side's strongest points survive contact with the other.

**The federation-first case** rests on four pillars. Freshness: a mediator answering for an AI agent must answer about data as it is now, and the most widely deployed self-hosted analytics tool, Metabase, stores no copy of user data at all — "all that processing happens inside your database" ([Metabase architecture guide](https://www.metabase.com/learn/metabase-basics/administration/administration-and-operation/metabase-and-your-db)). Governance: live connections inherit the source's own grants and row-level security, while a local copy is a second, ungoverned dataset. Time-to-first-value: ATTACH a connection string and query in minutes, versus choose-tables-sync-and-wait. Market validation: Trino/Presto proved query-in-place at petabyte scale and Starburst built a company on "connect directly to data where it lives" ([Starburst](https://www.starburst.io/trino/)), while MotherDuck's CIDR-reviewed dual execution proved a DuckDB planner can cost-route single queries across local and remote data, with follow-on research reporting up to 17x speedups ([MotherDuck CIDR paper](https://motherduck.com/blog/cidr-paper-hybrid-query-processing-motherduck/)). Its sharpest structural argument: every federation weakness is fixed by *adding* a component (replica, cache, result store), while every ingest weakness is fixed only by *building live connectivity anyway* — so federation-first is the lower-regret ordering.

**The ingest-first case** answers with physics and precedent. A spreadsheet is the most latency-intolerant analytical UI there is — every scroll and formula edit is a query — and remote queries are floor-bounded by network RTT with a fat latency tail that interactivity cannot amortize; DuckDB's own measurements put native storage at roughly **10x faster than scanning the same data live from Postgres** ([DuckDB postgres scanner post](https://duckdb.org/2022/09/30/postgres-scanner.html)), and DuckDB v1.4 is the fastest system on ClickBench once data is local ([DuckDB v1.4 benchmark](https://duckdb.org/2025/10/09/benchmark-results-14-lts.html)). Pushdown is unreliable and fails silently: a documented case shows a filter that didn't push down forcing a 10-second full remote scan where raw `postgres_query()` returned in milliseconds ([duckdb-postgres #369](https://github.com/duckdb/duckdb-postgres/issues/369)), and MySQL pushdown remains experimental and off by default. Reproducibility: an agent answer receipt is only auditable if the bytes it computed over can be replayed, and a live Postgres mutates underneath you — while a local snapshot (DuckDB file, Parquet, DuckLake with its snapshot-per-transaction time travel ([DuckLake docs](https://duckdb.org/docs/lts/core_extensions/ducklake))) is a stable, hashable artifact.

**Verdict.** The positions are closer than they look: the federation side concedes outright that "a spreadsheet grid recomputing interactively over a remote-only source is not viable," and the ingest side concedes warehouse scale and strict residency to federation. The real disagreement is ordering and defaults, and there the federation side's asymmetry argument is decisive *for the architecture* while the ingest side's physics is decisive *for the serving path*. The verdict: **build federation-first, serve ingest-first.** DuckDB is the single planner; remote sources ATTACH live and remain the source of truth; but no interactive surface — grid repaint, formula recompute, agent iteration loop — ever runs against a remote scan. Instead, every remote query's bounded result is materialized into local revision-stamped storage, and the grid, the formula engine, and the agent's follow-up tools all read that materialization. This also unifies the receipt problem: a receipt pins the materialized artifact (hash + snapshot/revision IDs) for mutable OLTP sources, and pins durable snapshot IDs directly for Iceberg/Delta sources, where federation is strictly better than copying because the source itself is versioned columnar storage ([DuckDB Iceberg catalogs](https://duckdb.org/docs/current/core_extensions/iceberg/catalogs.html)).

The conditions under which each side wins should be stated in Alephgrid's own docs. **Federation wins** when the user already owns a queryable Postgres/warehouse/lake (the assumed target persona); when data is compliance-bound or too large to copy; when sources are Iceberg/Parquet (nothing better to ingest into); and when the agent's answer must reflect the present. **Ingest wins** when sources are files and APIs (nothing to federate to); when the workload is the interactive grid itself; when answers must be replayable; when the source is an OLTP primary without a replica (per-source connection caps and a "this looks like a prod box" warning are mandatory); when connectivity is intermittent or the deployment is offline; and when the source is MySQL-only today (honestly a Tier-3 federation target). **Either side's position collapses** on one untested assumption: no telemetry yet shows whether Alephgrid's real users arrive with warehouses or with CSVs — if adoption is dominated by local files, the federation layer is plumbing, and that is the single highest-value thing to instrument at launch. Operationally, the verdict means shipping four things together: per-source connection caps, EXPLAIN-based preflight scan estimates with guardrails ("this will pull ~40M rows — materialize instead?"), source-dialect raw passthrough (`postgres_query()`-style) as the guaranteed-pushdown escape hatch, and freshness records on every materialization ({source snapshot token, fetched_at, watermark}) with Sling-style `MAX(update_key)` incremental refresh ([Sling replication docs](https://docs.slingdata.io/sling-cli/run/configuration/replication)) before any CDC sidecar is considered.

## The agent harness is a three-tier tool surface over curated, searchable context

The harness research confirms and sharpens the earlier trusted-agent conclusions rather than overturning them. On tool granularity, the field converged on a spectrum: dbt measured **98.2–100% accuracy for semantic-layer metric queries vs 84.1–90% for text-to-SQL** with the same models and questions — but 0% outside the modeled scope, because the semantic layer errors rather than guesses ([dbt 2026 benchmark](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)); Cube deliberately chose "Semantic SQL" over governed views — flexible SQL constrained to governed measures, linted before execution — over both raw SQL and rigid JSON plans ([Cube harness post](https://cube.dev/blog/building-an-agentic-analytics-harness)); and real-enterprise benchmarks show free-form agents remain unsolved at scale, with Spider 2.0-DBT (the DuckDB-native, repository-level split — the most relevant public benchmark for Alephgrid) topping out at **65.6%** ([spider2-sql.github.io](https://spider2-sql.github.io/)). Alephgrid's agent surface should therefore be three tiers: (1) metric-registry queries for governed questions, built on the earlier research's "compact versioned metric contract" (metric ID, measure, grain, dimensions, join keys, null policy) with each answer exposing the definition it used; (2) constrained SQL over curated views for exploration; (3) raw SQL only as an audited escape hatch behind the same policy checks. The "refuse outside scope" failure mode is a feature to copy, and Databricks' trusted assets and Snowflake's verified queries — human-verified parameterized queries that mark responses as trusted ([Genie trusted assets](https://docs.databricks.com/genie/trusted-assets.html)) — map directly onto Alephgrid's answer-receipt concept: a receipt cheaply carries "trusted: derived from verified query X," and promoting a successful agent analysis into the verified-query store doubles as both an accuracy and a cost optimization.

On context engineering, the measured evidence says the cheap default is **schema cards = DDL + 3–5 sample values per column + row count**: MotherDuck's study found sample values alone worth ~+7 points of execution accuracy, and query-log-derived schema descriptions worth **+16 points** on their production warehouse for Gemini 2.5 Flash — while the same context *hurt* a smaller model by 8–10 points, so per-model context budgets are required, not one fat prompt ([MotherDuck research](https://motherduck.com/research/query-log-informed-schema-descriptions-text-to-sql/)). Context should be served through a `search_catalog` tool returning compact, access-filtered candidates rather than preloaded — Cube and dbt both converged there, and dbt states flatly that full-schema context "is impractical for larger datasets" ([dbt benchmark](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)). A query-log-mining job that proposes column descriptions is a differentiator a mediator is uniquely positioned to ship, since it sees every query. On efficiency, the field validated the ResultHandle design wholesale: Cube returns the first 100 rows + total count + query ID + truncation flag ([Cube harness post](https://cube.dev/blog/building-an-agentic-analytics-harness)); Superglue built MCP result pagination and then deleted it, concluding "big results belong in a file the agent can query, not in the prompt" ([superglue blog](https://superglue.ai/blog/mcp-tool-result-limits/)); Anthropic's code-execution-with-MCP work keeps intermediate results out of model context entirely ([Anthropic research](https://www.anthropic.com/research/code-execution-with-mcp)). Alephgrid has a structural advantage here: because it *is* a DuckDB engine, the "file the agent can query" is a snapshot-pinned temp table behind the handle, served by `fetch_rows`, `aggregate`, and `sample` follow-up tools — pass-through MCP servers cannot offer that. Error messages with recovery hints ("retry identifier in quotes") are a cheap, field-reported lever against agent retry loops.

The spreadsheet-specific evidence argues for routing agents through structured tools, not free-form grid editing: the best Excel-native agents score ~59% on SpreadsheetBench (a benchmark their vendor helped build) and ~75% in independent testing with reliability complaints ([AIMultiple](https://aimultiple.com/ai-excel)) — far below the ~98% of semantic-layer querying — and the independent OSS project GridOS converged on exactly Alephgrid's proposal-first design, with the LLM "physically blocked from writing directly to the cells" behind a collision-checked preview step ([dev.to](https://dev.to/shreydevkar/i-built-an-open-source-ai-spreadsheet-that-doesnt-hallucinate-math-25g8)). Direct grid mutation should remain the most proposal-gated path, per the earlier research's commit protocol (plan hash + source revision + actor + expiry + idempotency key, recheck on commit). Finally, evals are both infrastructure and marketing: adopt Spider 2.0-DBT as the external yardstick, dbt's published harness ([dbt-llm-sl-bench](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)) as the template for metric-vs-SQL internal evals, SpreadsheetBench for grid tools, and AgentDojo's utility-plus-security pattern ([AgentDojo in inspect_evals](https://ukgovernmentbeis.github.io/inspect_evals/evals/agentdojo/index.html)) extended with a DuckDB environment where injected strings arrive *inside query results* — a confirmed gap in every existing suite and a credible OSS contribution. Keep the verified-query store (context) and the eval set (grading) as strictly disjoint artifacts, as Genie does ([Genie concepts](https://docs.databricks.com/aws/en/genie/concepts)), to avoid contaminating your own harness. Treat absolute leaderboard numbers skeptically throughout: measured annotation error rates run **52.8% for BIRD Mini-Dev and 66.1% for Spider 2.0-Snow** ([CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p5-jin.pdf)), so use relative deltas.

## Speed comes from DuckDB currency, data layout, Arrow transport, and revision-keyed caching

The performance evidence orders the levers by measured payoff, and the biggest one is nearly free: **track DuckDB releases aggressively** — the engine's own benchmark-over-time shows a full db-benchmark run dropping from ~500s (v0.2.7, 2021) to under 35s today ([Benchmarking Ourselves over Time](https://duckdb.org/2024/06/26/benchmarks-over-time)), so re-bumping the pinned crate each DuckDB minor outperforms any application tuning. Second is physical layout: keeping tables clustered on the grid's row-order key exploits automatic zonemaps for **~1.5x faster queries and ~2.5x smaller storage** per the docs' own measurements, while ART indexes should be avoided for grid filtering (their memory is never evicted under pressure) ([DuckDB indexing guide](https://duckdb.org/docs/2.0/guides/performance/indexing.html)); on shared hosts, cap `memory_limit` below the 80% default, set `temp_directory` for spill, and disable `preserve_insertion_order` on big imports ([How to Tune Workloads](https://duckdb.org/docs/2.0/guides/performance/how_to_tune_workloads.html)). Third is transport and caching: serialize grid pages as **Arrow IPC** from axum (the duckdb crate exposes Arrow record batches natively) — the one directly comparable migration measured ~39% smaller payloads and ~150ms faster large fetches versus JSON ([hotdata-cli PR #103](https://github.com/hotdata-dev/hotdata-cli/pull/103)) — and cache result pages at the Arrow-bytes level keyed by (normalized-SQL hash, table `data_rev`), which is Rill's cache-key pattern made exact and needs no TTLs because Alephgrid already tracks per-table revisions. Mosaic demonstrates what the interaction layer can reach with caching, query consolidation, and speculative prefetch: author-claimed sub-100ms, often 1–10ms, interaction over millions-to-billions of rows ([Why Mosaic](https://idl.uw.edu/mosaic/why-mosaic)). Since DuckDB has no materialized views or production IVM, formula recomputation should stay application-level: a column dependency DAG from the formula compiler, row-scoped `UPDATE ... FROM` recompute when the edit's row set is known, full-column recompute as fallback — safe under DuckDB's MVCC model where read-only transactions and appends never conflict ([Analytics-Optimized Concurrent Transactions](https://duckdb.org/2024/10/30/analytics-optimized-concurrent-transactions)). On the paging path, prefer keyset cursors (`WHERE ord > ? LIMIT n`) over OFFSET so zonemaps prune row groups, wire every paging job to duckdb-rs's `InterruptHandle` so superseded scroll queries cancel, and keep formula recomputes on the existing single-writer queue. These choices also make Alephgrid's repeated sub-100ms grid queries the exact regime where cached prepared statements are documented to pay off ([How to Tune Workloads](https://duckdb.org/docs/2.0/guides/performance/how_to_tune_workloads.html)).

## The roadmap: six layers, in dependency order

The earlier trusted-agent research settled the foundation, and nothing in the new notes disturbs it: Alephgrid's position is **the governed analytical workspace where humans and agents work on the same data** — accountable execution, durable shared artifacts, and controlled change, not a faster database socket — and the sequencing is identity and Cedar-style embedded authorization *first*, then the read-only MCP gateway, because protocol annotations are not enforcement and a gateway without per-principal policy is just a credential with extra steps. Answer receipts (artifact ID + source revisions + plan + policy version + truncation flags) and proposal-first mutations remain the two signature mechanisms; this report's findings slot the remaining layers around them. **Layer 1 — identity/authorization gate** (from prior research: OIDC, space membership, deny-by-default routes, Cedar evaluated as the embedded Rust decision layer). **Layer 2 — read-only agent gateway** with the three-tier tool surface, schema cards with sample values, `search_catalog`, ResultHandles backed by snapshot-pinned temp tables, and recovery-hint errors. **Layer 3 — the connector broker**: structured-field connections (the Metabase lesson), server-held secrets with short-lived tokens, Tier-1 core extensions default-on, READ_ONLY ATTACH by default, per-source connection caps, SSRF hardening, and scan-size preflight guardrails. **Layer 4 — the materialization/cache tier that implements the debate verdict**: bounded result materialization always-on; freshness records with watermark-based incremental refresh (Sling/dlt patterns, shell-out before build); `last_synced_at` surfaced in the UI and in every receipt; DuckLake evaluated as the snapshot substrate once its maturity is confirmed (its GA dates were not primary-source verified). **Layer 5 — the semantic registry and verified-query store**, native and compact first, MetricFlow/Cube import adapters later ([MetricFlow is now Apache-2.0](https://www.getdbt.com/blog/open-source-metricflow-governed-metrics)). **Layer 6 — the public eval suite** (Spider 2.0-DBT target, SpreadsheetBench, the SQL-results injection benchmark that doesn't yet exist anywhere). Arrow IPC transport and the revision-keyed cache are cross-cutting and can land with Layer 2.

## Conclusion

The two research passes, read together, show that Alephgrid's hardest questions are already answered by other people's scar tissue: GlareDB answers "should we build connectors" (no — broker DuckDB's), Metabase's CVE trail answers "how do we accept connections" (structured fields, never strings), the physics of grid interaction answers "can the spreadsheet federate" (no — materialize), MotherDuck's CIDR work answers "can one planner span local and remote" (yes), and Quadratic's license flip answers "is the open niche real" (it is, and it is currently empty). What remains genuinely unresolved is not architectural but empirical: whether Alephgrid's first thousand users arrive holding warehouse credentials or CSV files, which determines how much of the federation spine gets exercised — so source-type telemetry should ship in the first release alongside the features it will adjudicate.

The deeper synthesis is that the debate's two sides were describing the same system from different ends, and the mediator framing dissolves the conflict: an agent-safety requirement (bounded blast radius — agents must not trigger unbounded remote scans), a UX requirement (sub-100ms grid interaction), and a trust requirement (replayable answer receipts) all independently demand the same component — default-on bounded materialization over live-attached sources. Alephgrid's differentiation is not that it connects to everything or that it is fast; Trino connects and DuckDB is fast. It is that every answer, human- or agent-produced, is a governed, reproducible, inspectable artifact that both can pick up where the other left off — and that no SaaS incumbent can follow it into self-hosted open source without abandoning their business model.

After the owner stipulated that users arrive with all source types (CSV, Parquet, S3, operational DBs, warehouses) from day one, four adversarial agents debated build priority and stack across two rounds (openings + cross-rebuttals: connectivity-first vs agent-gateway-first vs engine/materialization-first, plus a stack stress-test covering DuckDB vs chDB/ClickHouse/DataFusion/Polars, storage, transport, and compute placement). Full transcript in research_notes/Alephgrid agent data mediator roadmap/discussion_*.md; resolved verdict and final two-quarter sequence in discussion_VERDICT.md.

Headline outcomes: the stack holds (embedded DuckDB, DuckDB-file-per-workbook now with DuckLake as a committed exit for receipt replay, Arrow IPC over HTTP/2 — not Flight SQL, server-side compute); build order converged on Layer-0 observability → minimal identity gate → engine core (Arrow IPC, revision-keyed cache, keyset paging, cancellation) → narrow hardened connectivity (S3 + Postgres READ_ONLY) → always-on materialization → thin read-only agent gateway late Q2 with tiered receipts (content-hash verification now, DuckLake time-travel later); ADBC warehouses and the broad connector fleet move to Q3 with kill criteria to pull them forward. Two new engineering risks priced in: the duckdb-rs FFI pin (mitigate with an internal connection trait + CI against libduckdb-sys HEAD) and the beta Quack client-server protocol (v1.5.3), which may relax the single-writer assumption at v2.0.
