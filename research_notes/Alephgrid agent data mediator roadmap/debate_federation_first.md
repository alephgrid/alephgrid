# Debate Position: Federation-First for Alephgrid

**Assigned position:** Alephgrid (self-hosted OSS, Rust/axum + embedded DuckDB analytical spreadsheet, mediator between AI agents, users, and data sources) should connect LIVE to external databases (Postgres, MySQL, S3/Parquet, Iceberg, warehouses) and push queries down to them, using DuckDB mainly as a federation/compute engine over ATTACHed sources — keeping data where it lives. These are argumentative notes: the strongest case FOR, anticipated objections from the ingest-first side, rebuttals, honest concessions, and verdict conditions. Current as of late 2026.

## Why live connectivity wins (freshness, no duplicate storage, governance at source, time-to-first-value)

### Takeaway
Direct-connect won in BI because the data most users want to analyze already lives in a queryable database, and the fastest path to a correct, fresh, governed answer is to query it in place. Metabase — the most widely deployed OSS self-hosted BI tool and the closest deployment analog to Alephgrid — stores no copy of user data at all; a copy pipeline is an entire second product (connectors, schedulers, schema drift handling, backfills) that an OSS spreadsheet team should not build before product-market fit.

### Cited Findings
- Metabase's official architecture guide: "all that processing happens inside your database, and all that Metabase sees is the query that you write, and the results that the query returns." Metabase keeps only schema metadata and column *samples* from sync/scan — "it doesn't store complete columns" — never the data itself — [Metabase: How Metabase works with your database](https://www.metabase.com/learn/metabase-basics/administration/administration-and-operation/metabase-and-your-db)
- Metabase's connection model is a database user account with granted privileges: "For Metabase to connect, query, or write to your database, you must give Metabase a database user account" — i.e., access control stays in the source database's own grant system, not in a copied store — [Metabase docs: Connecting to databases](https://www.metabase.com/docs/latest/databases/connecting)
- Starburst (Trino's commercial steward) describes the federation value proposition that built a company on it: Trino "connects directly to data where it lives, such as data lakes, data warehouses, operational databases, and SaaS APIs, without requiring a copy," with joins in one SQL statement across "Snowflake, Amazon S3, Postgres, Kafka, and 50+ other sources," and "predicate pushdown to each source" so you "only pull what you need" — [Starburst: Trino](https://www.starburst.io/trino/)
- MotherDuck on the DuckDB postgres extension's freshness/consistency property: reads "use transactional snapshots, so results are consistent," and the pattern isolates the OLTP box because "the analytical heavy lifting happens on the DuckDB side" — [MotherDuck: PostgreSQL and Ducks](https://motherduck.com/blog/postgres-duckdb-options/)
- The same MotherDuck post names the federation sweet spot explicitly: ideal for "ad-hoc analysis and smaller tables," and even when you DO want a copy, the extension itself is the simplest copy mechanism — "a simple full-refresh data pipeline" when "the data is small enough that a full-refresh is cost-effective" — [MotherDuck: PostgreSQL and Ducks](https://motherduck.com/blog/postgres-duckdb-options/)
- Practitioner evidence that direct-connect is how self-hosters actually deploy: an Odoo community user runs Metabase with no ETL layer (via a Postgres instance using FDW to sources), citing "real-time reporting and less complexity," with "performance good enough so far" and a read replica as the escape hatch — [Odoo community thread, Apr 2025](https://odoo-community.org/groups/contributors-15/contributors-2041231)

### Inferences
- **Freshness is not a nice-to-have for Alephgrid's stated mission.** An AI agent mediating between a user and their operational data must answer about the data *as it is now*. Any ingest pipeline introduces a staleness window the agent cannot see past, and "the dashboard says X but the database says Y" is exactly the trust failure a mediator product cannot afford. Federation makes freshness the default and staleness an explicit, opt-in choice (a cached table with a timestamp).
- **Governance stays enforceable.** With live connections, the source database's own roles/grants/row-level security apply to every query Alephgrid (or an agent through Alephgrid) issues. The moment you copy data into a local DuckDB file, you have created a second, ungoverned copy whose access control is whatever the Alephgrid host's filesystem permissions are. For compliance-bound users (the self-hosted OSS audience skews this way), "we never copy your data out of your database" is a one-sentence security story; "we copy it but we re-implement your access policies" is a multi-quarter engineering program.
- **Time-to-first-value:** a user with an existing Postgres/warehouse types a connection string and is querying in minutes (`ATTACH 'postgres://...'`). Ingest-first requires choosing tables, running an initial sync, waiting, and then maintaining that sync. For an OSS project trying to convert a curious self-hoster in their first 15 minutes, this difference is existential.
- **No duplicate storage cost or capacity planning.** A self-hosted Alephgrid instance federating over a 2 TB warehouse needs disk for results and caches, not for 2 TB. Ingest-first makes the Alephgrid host's disk a hard scaling bottleneck and a second thing to back up.

### Gaps
- I found no rigorous independent study quantifying "why direct-connect won in BI" as a market outcome; the evidence is architectural documentation (Metabase, Trino/Starburst) plus practitioner anecdote, not a market analysis. Note also that Looker/Metabase-style direct connect mostly targets *warehouses* already optimized for analytics; the claim transfers to OLTP sources only with the caveats in the weaknesses section.

## Is DuckDB federation technically viable? (pushdown reality, Iceberg/Delta, ADBC)

### Takeaway
Yes, with sharp edges. DuckDB's postgres extension is a genuinely engineered federation path (binary wire protocol, parallel TID-range scans, exported-snapshot consistency, filter pushdown on by default in current docs, and a remote-pushdown optimizer that ships whole queries to Postgres), and the Iceberg extension now ATTACHes REST catalogs with reads *and writes*. But pushdown is shallow — filters and projections, not joins or aggregates — so performance falls off a cliff on large remote tables when the heavy operators must run DuckDB-side over the network. The honest claim is "federation with bounded scans and a pushdown-aware planner," not "federation is free."

### Cited Findings
**Postgres extension — what actually works:**
- The original DuckDB postgres scanner design: it uses "the rarely used binary mode of the client-server protocol" (format "quite similar to the on-disk representation of Postgres data files," avoiding string conversion), parallelizes scans across connections by TID page ranges, and achieves snapshot consistency by opening a read-only transaction and exporting it via `pg_export_snapshot()` so all parallel connections "see the table state exactly as it appeared at the very beginning of our scan" — [DuckDB blog: Querying Postgres Tables Directly from DuckDB (2022)](https://duckdb.org/2022/09/30/postgres-scanner.html)
- Benchmark from that post (TPC-H SF1, DuckDB 0.5.1 vs Postgres 14.5, single M1 Max): DuckDB-over-postgres-scanner beat stock Postgres on roughly half the 22 queries (9/22 by count in the results table); stock Postgres *timed out* on Q17 and Q20 (correlated subqueries) which the scanner finished in under a second; native DuckDB storage was ~10x faster than scanning Postgres — [DuckDB blog, 2022](https://duckdb.org/2022/09/30/postgres-scanner.html). Caveat: small scale factor, old versions, vendor's own benchmark.
- Current (DuckDB 2.0) postgres extension docs: `pg_enable_filter_pushdown` **defaults to true** (the 2022 post had it default-off — this matured); `pg_use_binary_copy` defaults to true; parallel ctid scan on by default (`pg_use_ctid_scan`, `pg_pages_per_task`=1000); isolation level configurable (READ COMMITTED / REPEATABLE READ / SERIALIZABLE, default REPEATABLE READ); and notably a **remote pushdown optimizer**: in a `CONNECT`-routed session it "ships queries directly to the PostgreSQL server instead of pulling tables over the wire" — [DuckDB docs: PostgreSQL extension (2.0)](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html)
- The docs themselves recommend the hybrid escape hatch: "create a copy of the PostgreSQL databases in DuckDB to prevent the system from re-reading the tables" via `CREATE TABLE ... AS FROM postgres_db.tbl` or `COPY FROM DATABASE` — [DuckDB docs, PostgreSQL extension](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html)

**Where pushdown falls off a cliff:**
- MotherDuck's comparison: the extension supports "some projection and filtering pushdown," but "when complex operations cannot be pushed down to PostgreSQL, they happen on the DuckDB side," which can move more data than needed; "data travels over the network from PostgreSQL to DuckDB, which can slow things down for large tables"; it is "often faster than native PostgreSQL for complex analytics, but slower than if that same data were in DuckDB's native storage format" — [MotherDuck: postgres-duckdb-options](https://motherduck.com/blog/postgres-duckdb-options/)
- Field report of the cliff: a duckdb-postgres GitHub issue where a filtered query was NOT pushed down, forcing a full remote table scan (10s+) while the same filter via `postgres_query()` (raw SQL to Postgres, index used) returned in milliseconds — [duckdb/duckdb-postgres issue #369](https://github.com/duckdb/duckdb-postgres/issues/369). Lesson: pushdown is real but not guaranteed; a product must verify with EXPLAIN and provide a raw-passthrough path.
- MySQL extension: filter pushdown is governed by `mysql_experimental_filter_pushdown`, **off by default and marked experimental** — materially weaker than the Postgres path — [duckdb.org MySQL extension docs](https://duckdb.org/docs/extensions/mysql.html) and the extension's configuration table (via [datadu-de/duckdb-mysql-sqlserver notes](https://github.com/datadu-de/duckdb-mysql-sqlserver)). Concession: MySQL federation is second-class today.

**Lakehouse formats:**
- DuckDB's iceberg extension ATTACHes Iceberg REST catalogs; "attaching a catalog is required for writing to Iceberg"; "reads and writes work with the default ATTACH options, including CREATE SCHEMA, CREATE TABLE, INSERT, and DROP TABLE"; documented setups for Polaris, Lakekeeper, Cloudflare R2, BigLake, AWS Glue, and S3 Tables; storage backends currently limited to S3, S3 Tables, and GCS — [DuckDB docs: Iceberg catalogs](https://duckdb.org/docs/current/core_extensions/iceberg/catalogs.html)
- Iceberg/Parquet-on-S3 is the one federation target with **no pushdown problem at all**: Parquet is columnar with zone-map/row-group statistics, which is DuckDB's native scanning fast path — this is the same architecture every lakehouse engine uses (inference flagged as such below).

**ADBC (the connector substrate for everything else):**
- ADBC is the Apache Arrow database connectivity standard "focused on bulk columnar data retrieval and ingestion through an Arrow-based API," complementary to JDBC/ODBC; API standard 1.0.0; implementations in C/C++, Go, Java, Python, R, .NET and more; it is client-side (per-database drivers + a driver manager) — [Apache Arrow: ADBC format docs](https://arrow.apache.org/docs/format/ADBC.html), [apache/arrow-adbc](https://github.com/apache/arrow-adbc/)
- Vendor adoption signal: ClickHouse shipped an official ADBC driver — [ClickHouse blog](https://clickhouse.com/blog/introducing-the-clickhouse-adbc-driver). (A secondary aggregator claims dbt Fusion is ADBC-exclusive and Power BI defaults new connections to ADBC; unverified against primary sources — treat as unconfirmed.)

### Inferences
- **The viability picture is tiered, and Alephgrid should say so in its architecture docs:** Tier 1 (excellent): Parquet/CSV on S3/HTTP, Iceberg via REST catalog — columnar, stat-pruned, parallel; federation is strictly better than ingest here because there is nothing to ingest *into* that is better. Tier 2 (good with care): Postgres — binary protocol, parallel snapshot-consistent scans, filter pushdown on by default, remote-pushdown optimizer, plus `postgres_query()` passthrough as the guaranteed-pushdown fallback. Tier 3 (weak): MySQL (experimental pushdown, off by default) and anything reached only via generic protocols — for these, "attach + cache" should be the default posture, and ADBC/Arrow is the right Rust-friendly substrate for warehouse connectors (Snowflake, BigQuery) rather than hand-rolled drivers.
- **The 2022→2026 trendline is my strongest dynamic argument:** filter pushdown went from default-off experimental to default-on; a remote pushdown optimizer appeared; Iceberg went from read-only preview to read/write catalog ATTACH. Betting Alephgrid's architecture on DuckDB federation is betting on a curve that has visibly bent upward for four years, maintained by someone else (DuckDB Labs) for free — the OSS leverage argument.
- **Pushdown unpredictability is a UX problem Alephgrid can solve above the engine:** surface EXPLAIN-derived "this query will scan N remote pages" estimates before execution, and fall back to source-dialect passthrough (postgres_query) when DuckDB's planner won't push a selective filter. A spreadsheet mediating for agents is exactly the layer where a query-cost guardrail belongs.

### Gaps
- No independent (non-vendor) benchmark of the *current* (2.0-era) postgres extension at realistic scale; the only hard numbers are DuckDB's own 2022 SF1 run and anecdotal issue reports. Honest unknown: where exactly the cliff sits in 2026 (table size × selectivity × network).
- I did not verify current DuckDB **Delta Lake** extension capabilities this session; Iceberg claims above are verified, Delta is not — do not cite Delta parity without checking [duckdb.org core_extensions/delta].
- No documented pushdown capability matrix for DuckDB's postgres extension (which predicates/functions push down vs not); the GitHub issue shows the docs under-specify this.

## Do real products validate federation-first? (Trino, MotherDuck, Metabase, ATTACH workflows)

### Takeaway
Three independent product lineages validate the model at different scales: Trino/Presto proved query-in-place federation at Facebook/Netflix petabyte scale; Metabase proved zero-copy direct connect is what the self-hosted OSS analytics market actually deploys; MotherDuck proved (with a peer-reviewed CIDR paper) that a DuckDB-based planner can split a single query across locations — which is precisely Alephgrid's "attach + cache" end-state, not a competing model.

### Cited Findings
- Presto was built at Facebook in 2012 because Hive was too slow at Facebook's scale; Facebook's engineering blog reported Netflix running ~3,500 Presto queries/day, and Netflix disclosed using Presto over ~10 PB in S3; the creators forked to PrestoSQL in 2018, renamed Trino in 2020, and Trino became the dominant branch — [Facebook Engineering: Building the Presto community](https://engineering.fb.com/core-data/building-the-presto-community/), [Wikipedia: Presto (SQL query engine)](https://en.wikipedia.org/wiki/Presto_(SQL_query_engine)), [Starburst: Presto vs Trino history](https://starburst.io/data-glossary/presto-sql-query-engine). Starburst raised a company to enterprise scale on exactly the "query data where it lives" pitch — [Starburst: Trino](https://www.starburst.io/trino/), [VentureBeat: Trino turns 10](https://venturebeat.com/business/trino-turns-10-starburst-celebrates-a-decade-of-its-open-source-query-engine)
- MotherDuck's dual execution (formerly "hybrid execution"): queries are "automatically routed to the optimal location: local DuckDB, MotherDuck cloud, or both," with joins between laptop-local and cloud data planned by a cost-based optimizer — [MotherDuck docs: Architecture and capabilities](https://motherduck.com/docs/concepts/architecture-and-capabilities/), [MotherDuck docs: Running dual execution queries](https://motherduck.com/docs/key-tasks/running-hybrid-queries.md)
- The approach is peer-reviewed: MotherDuck presented hybrid query processing at CIDR 2024 — [MotherDuck: CIDR paper on hybrid query processing](https://motherduck.com/blog/cidr-paper-hybrid-query-processing-motherduck/) — and follow-on research on cost-based local/cloud split reports up to 17x speedups on long analytical queries — [MotherDuck research: cost-based hybrid query optimization](https://motherduck.com/research/cost-based-hybrid-query-optimization-in-motherduck.md)
- Metabase: zero data ingestion by design (see section 1 citations); self-hosters deploy it direct-connect with read replicas as the load mitigation — [Metabase learn](https://www.metabase.com/learn/metabase-basics/administration/administration-and-operation/metabase-and-your-db), [Odoo community thread](https://odoo-community.org/groups/contributors-15/contributors-2041231)
- Counter-example I must report honestly from the same thread: a second Odoo practitioner chose "daily replication of the database, to not disturb operations," and noted Metabase "connects only to one database" (can't join across sources) — [Odoo community thread](https://odoo-community.org/groups/contributors-15/contributors-2039665). Two lessons: (a) some direct-connect users graduate to copies for load isolation — the hybrid pressure is real; (b) cross-source joins are a gap in Metabase that DuckDB ATTACH federation *natively solves* (multiple ATTACHed databases joinable in one query) — a differentiator, not a weakness, for Alephgrid.

### Inferences
- The market pattern across all three lineages is the same: **start federated, add caching/materialization as an optimization layer** — never the reverse. Trino added caching ecosystems (Alluxio etc.); MotherDuck's whole product is a cache/compute tier that still plans against local data; Metabase added model persistence. No successful product in this space started ingest-first and then bolted on live connectivity; the asymmetry is because a federation engine can always add a cache, but an ingest architecture's copy-store assumptions (schema snapshots, sync state, identity of "the" table) leak into every layer and resist retrofitting liveness.
- MotherDuck's CIDR-validated dual execution is the strongest proof that the DuckDB engine itself is architecturally suited to "some data here, some data there, one planner" — which is Alephgrid's exact topology (hot cached tables in local DuckDB + ATTACHed remote sources).

### Gaps
- Netflix/Lyft adoption numbers trace to vendor blogs and Wikipedia, not current first-party engineering posts; magnitudes are dated (2015-era). Directionally solid, precisely stale.
- No public case study of a *spreadsheet* product (as opposed to BI/query tools) succeeding with federation; the closest analogs (Excel PowerQuery, Google Sheets Connected Sheets) are ingest-on-refresh hybrids. The opposing side can fairly claim spreadsheets have historically been copy-based.

## Honest weaknesses, strongest objections, and rebuttals

### Takeaway
The ingest-first side has four genuinely strong objections: OLTP load, latency/interactivity (spreadsheets demand sub-second recalculation), snapshot/reproducibility for agent answer-receipts, and pushdown unpredictability. I concede each is real; none is fatal because each has a documented mitigation, and critically, the mitigations are *additive caching layers on a federation core* rather than architectural reversals. The one objection I concede outright: a spreadsheet grid recomputing interactively over a remote-only source is not viable — some local materialization is mandatory for the grid itself.

### Cited Findings
**Objection 1 — "Never run analytics on prod Postgres" (OLTP load):**
- Practitioner consensus is unambiguous: "The first rule of running analytics on Postgres: don't run analytics queries on your primary OLTP database" — one heavy query can stall the application; isolation protects "against runaway queries impacting production" — [Tinybird on DEV: Outgrowing Postgres](https://dev.to/tinybirdco/outgrowing-postgres-how-to-run-olap-workloads-on-postgres-282j)
- "Don't use the same server as your production system"; warehouses are built differently from transactional Postgres — [Towards Data Science: Using PostgreSQL as a data warehouse](https://towardsdatascience.com/using-postgresql-as-a-data-warehouse-23fb50fb2bb0/); advice against pointing BI tools like Tableau directly at production — [Cortance: what to avoid pairing with PostgreSQL](https://cortance.com/answers/postgresql/what-to-avoid-pairing-with-postgresql)
- *Rebuttal material:* the standard remedy in every one of these sources is a **read replica — which is still federation** (live connect to a replica), not ingestion. MotherDuck: "a dedicated read replica is highly recommended" — [MotherDuck](https://motherduck.com/blog/postgres-duckdb-options/); the Metabase self-hoster's plan was exactly "add a read-replica if issues arose" — [Odoo thread](https://odoo-community.org/groups/contributors-15/contributors-2041231). Note also DuckDB's scanner opens *read-only* snapshot transactions — [DuckDB blog](https://duckdb.org/2022/09/30/postgres-scanner.html) — the load risk is scan I/O and connection count, not locking. Concession retained: parallel TID scans (multiple connections × 1000 pages/task) can saturate a small instance's I/O and its connection slots; Alephgrid needs per-source connection caps and a "this looks like a prod OLTP box" warning by default.

**Objection 2 — latency / spreadsheet interactivity:**
- "Data travels over the network from PostgreSQL to DuckDB, which can slow things down for large tables"; recommended "only when network latency is acceptable" — [MotherDuck](https://motherduck.com/blog/postgres-duckdb-options/); native DuckDB storage ~10x faster than scanning Postgres even on localhost — [DuckDB blog](https://duckdb.org/2022/09/30/postgres-scanner.html)
- *Rebuttal:* this argues for **result materialization, not source ingestion**. A spreadsheet's unit of interaction is a query result region (thousands–millions of rows), not the source table (billions). Federate the query once; materialize the bounded result into local DuckDB; recalc the grid against the local copy; re-run the remote query only on explicit refresh. This is Metabase's result-cache pattern and MotherDuck's dual-execution pattern, and DuckDB's own docs bless it (`CREATE TABLE ... AS FROM postgres_db.tbl`) — [DuckDB docs](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html). Concession: for users who hammer the same large remote tables all day, scheduled hot-table caching is needed — i.e., the hybrid, not pure federation.

**Objection 3 — snapshot/reproducibility (answer receipts on mutable sources):**
- An agent-mediator that issues "answer receipts" needs the answer to be re-derivable; a live Postgres mutates underneath you. *Partial rebuttals from evidence:* (a) within one query, DuckDB's exported-snapshot mechanism guarantees a consistent point-in-time read — [DuckDB blog](https://duckdb.org/2022/09/30/postgres-scanner.html) — and REPEATABLE READ is the default isolation across a transaction — [DuckDB docs](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html); (b) Iceberg sources are *better* than local copies here — snapshot IDs are durable, so a receipt can pin "snapshot 12345" and anyone can re-read it — [DuckDB Iceberg docs](https://duckdb.org/docs/current/core_extensions/iceberg/catalogs.html); (c) for mutable OLTP sources, the receipt should pin the *materialized result* (hash + stored result set in local DuckDB), which federation-plus-bounded-materialization produces anyway. Concession: cross-query repeatability on a raw Postgres source is impossible without storing the result — ingest-first's cleanest point, answered by storing results (KBs–MBs), not sources (GBs–TBs).

**Objection 4 — pushdown unpredictability and connection exhaustion:**
- Documented failure: filter not pushed down → full remote scan, 10s+, vs milliseconds via `postgres_query()` — [duckdb-postgres #369](https://github.com/duckdb/duckdb-postgres/issues/369); MySQL pushdown experimental/off-by-default — [duckdb-mysql config](https://github.com/datadu-de/duckdb-mysql-sqlserver); parallel scanning multiplies connections (ctid ranges across connections) — [DuckDB blog](https://duckdb.org/2022/09/30/postgres-scanner.html)
- *Rebuttal:* these are engineering tasks at exactly the layer Alephgrid occupies: per-source connection pools with hard caps; EXPLAIN-based preflight cost estimates with scan-size guardrails ("this will pull ~40M rows — materialize instead?"); dialect passthrough (`postgres_query`) when the planner won't push; and the 2.0 remote-pushdown optimizer already ships whole queries to Postgres in CONNECT-routed sessions — [DuckDB docs](https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html). Concession: this is real engineering Alephgrid must own; "ATTACH and pray" is not a product.

### Inferences
- The decisive asymmetry: every weakness of federation is mitigated by **adding** a component (replica, cache table, result store, rate limiter) on top of an unchanged core. The weaknesses of ingest-first (staleness, duplicate storage, re-implementing governance, sync pipeline maintenance, slow first-run) are mitigated only by **adding live connectivity** — i.e., by building the federation layer anyway. Federation-first is therefore the lower-regret ordering even where the endgame is hybrid.
- For an agent mediator specifically, bounded materialization is doubly required anyway: agents should not be able to trigger unbounded remote scans (cost/load blast radius), so the "materialize bounded results locally" discipline serves both performance and agent-safety.

### Gaps
- No public postmortem was found of a company that shipped DuckDB-federation in a product and documented production failure modes (connection exhaustion, replica lag, etc.) — the strongest possible ingest-side evidence would be such a postmortem; I found none either way.
- No data on typical result-set sizes in spreadsheet analytics to quantify the "materialize results, not sources" storage claim.

## Verdict conditions: where federation-first wins and where it loses

### Takeaway
Federation-first is the right architecture for Alephgrid's core audience — self-hosters who already own a Postgres/warehouse/lake and compliance-bound teams who cannot copy data out — provided it ships with bounded result materialization and hot-table caching from day one. It loses for offline/laptop-grade analysis, chronically slow or flaky sources, and repeated full scans of huge mutable tables; those users need the cache tier to be first-class, which is a feature of the hybrid, not a refutation of the federation core.

### Cited Findings
- Federation sweet spot per MotherDuck: "ad-hoc analysis and smaller tables," environments where you can't install anything on the source, acceptable network latency; replica recommended for isolation — [MotherDuck](https://motherduck.com/blog/postgres-duckdb-options/)
- Lake/Iceberg workloads: full read/write federation with durable snapshots, no copy ever justified — [DuckDB Iceberg docs](https://duckdb.org/docs/current/core_extensions/iceberg/catalogs.html)
- Failure regime: large tables over the network ([MotherDuck](https://motherduck.com/blog/postgres-duckdb-options/)), non-pushed filters forcing full scans ([duckdb-postgres #369](https://github.com/duckdb/duckdb-postgres/issues/369)), MySQL's immature pushdown ([duckdb-mysql](https://github.com/datadu-de/duckdb-mysql-sqlserver)), and the universal "no analytics on prod OLTP" rule ([Tinybird/DEV](https://dev.to/tinybirdco/outgrowing-postgres-how-to-run-olap-workloads-on-postgres-282j))
- The resolution pattern, validated at CIDR: one planner over local + remote data, cost-routed — [MotherDuck CIDR paper](https://motherduck.com/blog/cidr-paper-hybrid-query-processing-motherduck/)

### Inferences
**Federation-first WINS when:** the user already owns a queryable source (Postgres/warehouse/lake) — the stated target persona; data is compliance-bound or too large to copy; freshness matters to the agent's answers; sources are Iceberg/Parquet (Tier 1, nothing to gain from copying); or the deployment is a resource-light self-hosted box that cannot host a second copy of the warehouse.

**Federation-first LOSES (ship the cache, or concede the workload) when:** the source is OLTP-primary with no replica and the workload is heavy (must cache or refuse); network latency is high or connectivity intermittent (offline analysis — local DuckDB tables are simply correct here, and Alephgrid should support plain local tables regardless); the workload repeatedly full-scans large mutable tables (cache the table, schedule refresh — at which point you've built a small ingest feature *inside* a federation product, which is the right containment); or the source is MySQL-only today (be honest in docs about Tier 3 status).

**Conditions under which my position is simply wrong:** if Alephgrid's real adoption turns out to be individuals analyzing CSVs/local files with no existing database (then federation is plumbing nobody uses and local-first was right); or if DuckDB's remote-source extensions stagnate or regress in reliability (the 2022–2026 trendline argues against this, but it is a dependency bet on DuckDB Labs' roadmap, not something Alephgrid controls).

**Recommended synthesis to carry into the debate:** federation-first ≠ federation-only. Architecture = DuckDB as the single planner; remote sources ATTACHed live as the default source of truth; bounded result materialization always-on (serves grid interactivity, answer receipts, and agent blast-radius control); opt-in hot-table caching with visible staleness timestamps; per-source connection caps and replica-detection warnings. Every component of this is individually evidenced above; the opposing side's best points (load, latency, reproducibility) are the *requirements list for the cache tier*, not arguments for inverting the architecture.

### Gaps
- No usage telemetry exists for Alephgrid itself (pre-launch), so the persona claim ("target users already own a database") is a product assumption, not an evidenced fact — the single biggest unknown on which this verdict turns.
