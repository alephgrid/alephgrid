# Universal Database Connectivity for Alephgrid (DuckDB-centered connector broker)

Research date: 2026-10-31. Product context: Rust/axum server with embedded DuckDB; goal is a mediator that lets users and AI agents connect to any database/data source, pushing heavy computation into DuckDB when the source can't handle it.

## Q1: DuckDB attach/scanner ecosystem (postgres, mysql, sqlite, httpfs/S3, Iceberg, Delta, DuckLake, Excel, Google Sheets, ODBC/ADBC paths)

### Takeaway
DuckDB's first-party scanner story is now genuinely strong: Postgres/MySQL/SQLite attach with read+write, Iceberg gained native writes in DuckDB 1.4.0 (Sept 2025), and Delta + Unity Catalog shed their experimental tags with write support in May 2026. The long tail (Google Sheets, ODBC) lives in community extensions, which are a different trust tier — DuckDB's own docs say to disable community extensions in services that execute untrusted SQL, which directly constrains Alephgrid's broker design.

### Cited Findings

**Postgres (core extension, `postgres`)**
- Writes are supported: the extension can create tables, ingest data, and run UPDATE/DELETE/ALTER TABLE/DROP/CREATE SCHEMA against the attached PostgreSQL database; all operations directly modify the Postgres database — [DuckDB postgres extension docs](https://duckdb.org/docs/stable/extensions/postgres); [current overview](https://duckdb.org/docs/current/core_extensions/postgres/overview.html)
- `ATTACH ... (TYPE postgres, READ_ONLY)` prevents modifications to the underlying database — [DuckDB postgres docs](https://duckdb.org/docs/stable/extensions/postgres)
- Filter pushdown is governed by the setting `pg_experimental_filter_pushdown`, described as "whether to use filter pushdown, currently experimental", default `true` — [DuckDB postgres docs](https://duckdb.org/docs/current/core_extensions/postgres/overview.html)
- DuckDB caches attached-schema metadata (table names, columns); the `pg_staleness_query_enabled` option checks Postgres `pg_class.xmin` per table on each query and reloads the cache automatically when a change is detected — [DuckDB postgres docs](https://duckdb.org/docs/current/core_extensions/postgres/overview.html)
- `postgres_execute()` runs arbitrary SQL inside Postgres, including schema-changing statements — important both as an escape hatch for full pushdown and as a privilege-escalation surface the broker must gate — [DuckDB postgres docs](https://duckdb.org/docs/stable/extensions/postgres)

**MySQL (core extension, `mysql`)**
- Official extension supports "reading and writing against a MySQL database"; it is a DuckDB-team extension at the "secondary support" tier (best-effort, still regularly updated) — [DuckDB core extensions overview](https://duckdb.org/docs/stable/core_extensions/overview)

**Excel (core extension, `excel`)**
- Reads and writes Excel files; export uses `COPY ... (FORMAT xlsx)`; only `.xlsx` supported, `.xls` is not; secondary-support tier — [DuckDB core extensions overview](https://duckdb.org/docs/stable/core_extensions/overview); [excel export guide](https://duckdb.org/docs/lts/guides/file_formats/excel_export.html)

**Iceberg / Delta / DuckLake**
- DuckDB 1.4.0 "Andium" (LTS, September 2025) added Iceberg write support; the duckdb-iceberg extension implements all data and metadata operations natively in the extension (no Spark/JVM dependency) — [x-cmd summary of the 1.4.0 release](https://www.x-cmd.com/blog/250921); official matrix at [DuckDB lakehouse formats page](https://duckdb.org/docs/lts/lakehouse_formats.html)
- DuckDB blog, 2026-05-07: "Delta Grows Up" — the Delta and Unity Catalog extensions are no longer experimental; now with writes, Unity Catalog and time travel support. Writes are plain INSERTs. Without catalog-managed tables (CMT), DuckDB writes go straight to the Delta log, so Unity Catalog can fall out of sync; with CMT, every write is staged and registered through UC before becoming visible. The UC extension cannot yet run CREATE TABLE DDL — CMT tables must be created via Spark or the UC CLI — [DuckDB blog: Delta/UC updates](https://duckdb.org/2026/05/07/delta-uc-updates.html)
- DuckLake: a third-party page claims DuckLake v1.0 went GA April 13, 2026 with 1.1 expected ~Sept 2026; I could not find a primary DuckDB/DuckLake release post in results, so treat the exact dates as unconfirmed — [smithery.ai skills page](https://smithery.ai/skills/vasilyu1983/data-lake-platform) (secondary source)

**Google Sheets (community extension, `gsheets`)**
- Read via `read_gsheet()` (accepts full URL, spreadsheet ID, or bare URL in FROM; options `headers`, `all_varchar`, `sheet='Name'`; `gid` in URL picks a sheet); write via `COPY <table> TO <sheet> (FORMAT gsheet)` with `create_if_not_exists`. Auth via `CREATE SECRET (TYPE gsheet)` (interactive browser OAuth) or `PROVIDER access_token, TOKEN '...'` (caller supplies a Google API access token). No ATTACH support documented; maintainers archiewood and mharrisb1 (~359 GitHub stars) — [DuckDB community extensions: gsheets](https://duckdb.org/community_extensions/extensions/gsheets)

**ODBC bridge (community extension, `nanodbc`)**
- Reaches any ODBC-compatible database from DuckDB: functions for scanning tables, running custom queries, and attaching whole sources as views; tested with SQL Server, MySQL, PostgreSQL, Snowflake, SQLite "and many other databases"; maintainer Hugoberry — [DuckDB community extensions: nanodbc](https://duckdb.org/community_extensions/extensions/nanodbc)

**Extension security model (core vs community)**
- Extensions are signature-checked on every load, in three categories: core-signed, community-signed, unsigned. Community extensions are open-source and distributed via the DuckDB Community Extensions repository, but "run third-party code"; DuckDB does not review submissions, only requires source availability, and recommends: "if you're running a web service that executes untrusted SQL from users with DuckDB, you should disable community extensions." Maintainers can pull problematic extensions from distribution quickly — [Securing Extensions, DuckDB operations manual](https://duckdb.org/docs/current/operations_manual/securing_duckdb/securing_extensions.html)

### Inferences
- The core/community split should map directly to Alephgrid's connector tiers: Tier 1 (postgres, mysql, sqlite, httpfs/S3, iceberg, delta, ducklake, excel — all core-signed, DuckDB-team-maintained, MIT-licensed as part of the duckdb org) can be enabled by default in a multi-tenant server; Tier 2 (gsheets, nanodbc, and other community extensions) should be opt-in per deployment, ideally behind a sandbox/worker-process boundary, because Alephgrid is exactly the "web service executing user SQL" case DuckDB's docs warn about.
- `pg_experimental_filter_pushdown` being both default-on and labeled experimental means the broker should surface per-query diagnostics (did the filter push down?) rather than assume it; EXPLAIN inspection of the scanner node is the practical check.
- The postgres/mysql/sqlite ATTACH model gives Alephgrid "live" cross-source joins for free (ATTACH several sources into one DuckDB catalog), but writes flowing straight through to production OLTP databases argue for defaulting every ATTACH to READ_ONLY and making writes an explicit, audited capability.
- From general knowledge (verify against docs before relying on it): `httpfs` is a core extension providing HTTP(S)/S3 reads with S3 writes via `COPY`, with credentials managed through DuckDB's Secrets Manager (`CREATE SECRET (TYPE s3, ...)`), and the `sqlite` core extension supports read/write ATTACH of SQLite files. Neither surfaced in search results this session, so cite duckdb.org core extension pages when writing the design doc.
- gsheets' "browser sign-in" secret type is unusable server-side; for Alephgrid the viable path is the `access_token` provider with tokens minted by Alephgrid's own Google OAuth app — which conveniently matches the credential-brokering design in Q5 (server holds refresh tokens, injects short-lived access tokens into the DuckDB secret).

### Gaps
- No primary-source confirmation of DuckLake 1.0/1.1 release dates or its current write/compaction feature set; needs a check of ducklake.select / duckdb.org blog.
- Did not find per-extension pushdown quality documentation for mysql/sqlite scanners (only postgres documents its pushdown setting); extent of projection/filter pushdown for mysql is undocumented in what I retrieved.
- No documented list of gsheets limits (row caps, rate limits, type coercion) on the extension page; duckdb-gsheets.com holds the detailed docs.
- Licensing of individual community extensions (gsheets, nanodbc) wasn't captured; each repo must be checked individually before bundling — community distribution does not imply a permissive license.

## Q2: ADBC and Arrow Flight SQL as universal driver layers

### Takeaway
ADBC's API standard is stable and Apache-2.0, with real drivers for Postgres, SQLite, Snowflake, BigQuery and Flight SQL — but the mature drivers are implemented in C/Go/Java, and the Rust story is a standalone `adbc_core` implementation plus a driver manager that loads foreign-language drivers as shared libraries. For Alephgrid, ADBC is the right fallback layer for warehouse sources DuckDB has no native scanner for (Snowflake, BigQuery), at the cost of shipping Go-built .so/.dylib driver binaries; it loses to native DuckDB scanners wherever those exist because ADBC gives you Arrow result transport, not pushdown-aware federation.

### Cited Findings
- ADBC is "an API standard for database access libraries ('drivers') in C, Go, and Java"; the API standard is "considered stable, but enhancements may be made"; the libraries are "under development"; license Apache-2.0; the repo contains binding/implementation folders for c, csharp, glib, go, java, javascript, python, r, ruby, and rust — [apache/arrow-adbc GitHub](https://github.com/apache/arrow-adbc)
- The Rust library is described as "a standalone implementation of the ADBC APIs", primary crate `adbc_core` — [ADBC Rust docs](https://arrow.apache.org/adbc/23/rust/index.html)
- ADBC's docs list driver packages for BigQuery, Flight SQL, and Snowflake (surfaced under the Python packaging in docs navigation); the JavaScript bindings are "experimental and built on the Rust driver manager" — i.e., a Rust driver manager exists and is load-bearing enough that another language binding sits on it — [ADBC docs](https://arrow.apache.org/adbc/current/javascript/)
- The authoritative per-driver, per-language matrix is the "Driver Implementation Status" page; my fetch of it returned empty content, so its specifics are unverified this session — [Driver Implementation Status](https://arrow.apache.org/adbc/main/driver/status.html)
- Third-party signal on driver maturity: a SQLAlchemy-ADBC dialect project notes Snowflake, BigQuery, and Flight SQL drivers "inherit the shared reflection path but have no per-driver CI" in that project — weak but consistent with "works, less battle-tested" — [drls-io/sqlalchemy-adbc](https://github.com/drls-io/sqlalchemy-adbc)

### Inferences
- From general knowledge (verify on the status page): the Snowflake, BigQuery and Flight SQL ADBC drivers are implemented in Go and distributed as cgo-built shared libraries; the Postgres driver is C++ on libpq; the SQLite driver is C. A Rust process (Alephgrid) consumes these via the ADBC driver manager's C FFI — meaning "ADBC support in Rust" is really "Rust driver manager + foreign shared-library drivers", with per-platform binary packaging as the main operational cost. DuckDB itself also exposes an ADBC entrypoint, so ADBC can even be the uniform internal interface if desired.
- When ADBC beats native scanners: (a) the source has no DuckDB scanner at all (Snowflake, BigQuery, Databricks SQL); (b) you want Arrow-native bulk result transport into DuckDB (`arrow` scan of record batches) with one uniform Rust-side API per source; (c) write-back via ADBC bulk ingest. When native scanners win: Postgres/MySQL/SQLite, where DuckDB's ATTACH gives catalog browsing, filter pushdown, and transparent SQL-level federation that ADBC cannot (ADBC executes whole SQL statements against the source; the mediator must itself decide what SQL to send — there is no automatic predicate pushdown layer).
- Arrow Flight SQL matters mostly as a server-side protocol Alephgrid could eventually *expose* (so BI tools/agents query Alephgrid over Flight SQL with JDBC/ADBC Flight SQL drivers), and as a client path to Dremio/InfluxDB 3-class sources. As a universal client layer to arbitrary databases it's weaker than ADBC because few databases speak Flight SQL natively.
- A pragmatic alternative worth noting for the design doc: for Snowflake/BigQuery, plain Rust client crates or the sources' own Arrow-returning APIs (BigQuery Storage Read API, Snowflake Arrow result format) can substitute for ADBC, but ADBC gives one interface instead of N bespoke integrations.

### Gaps
- Could not retrieve the ADBC Driver Implementation Status matrix (page fetched empty), so exact current per-driver feature/maturity grades (e.g., partitioned reads, bulk ingest support per driver, Rust driver-manager loading of Go drivers) are unverified; this is the single most important page to re-check before committing to ADBC.
- No benchmark data found this session comparing ADBC bulk extraction vs native scanners vs JDBC-style row transport.
- `adbc_core` crate version/maturity (API stability, production users) not established from results.

## Q3: Pushdown vs ingest — when to federate to the source vs copy into DuckDB

### Takeaway
Every federation engine converges on the same shape: push filters/projections (and sometimes aggregations/joins) to the source when the connector and query shape allow, and otherwise pull full tables — and the pulls are the performance cliff. Trino's docs are explicit that pushdown depends on connector + specific functions + query structure and can even backfire (join pushdown inflating row counts); DuckDB's postgres pushdown is a single experimental boolean. The design consequence for Alephgrid: treat pushdown as an unreliable optimization, make "what ran where" observable, and make materialize-into-DuckDB the default for repeated/interactive spreadsheet access.

### Cited Findings
- Trino: whether pushdown happens depends on the connector, on support for each specific function, and on the structure of the query; limit pushdown implementation is connector-specific — [Trino pushdown docs](https://trino.io/docs/current/optimizer/pushdown.html)
- Trino: join pushdown "can increase the row count relative to the join inputs, which may hurt performance", though joins are typically beneficial to push down — [Trino pushdown docs](https://trino.io/docs/current/optimizer/pushdown.html)
- Trino: pushdown success is verifiable in EXPLAIN — a successfully pushed predicate leaves no ScanFilterProject for that clause; an aggregate appearing as a separate plan operation means Trino is computing it itself — [Trino pushdown docs](https://trino.io/docs/current/optimizer/pushdown.html)
- Connector-specific pushdown gaps are normal, not exceptional: Cloudera's Trino-on-Impala connector documents unsupported Top-N pushdown and some aggregate/join variants, and that fixed-length CHAR columns skip source-side filtering entirely — filters on them are evaluated in memory on Trino — [Cloudera Trino connectors doc](https://docs.cloudera.com/cdw-runtime/1.5.5/trino-connectors/trino-connectors.pdf)
- Historical Presto planner post (2019): predicate pushdown was limited because "the expressiveness of what could be pushed down was restricted" and connectors could not change plan structure; the fix was richer connector optimization rules — background on why pushdown frameworks grow complex — [Presto blog](https://prestodb.io/blog/2019/12/23/improve-presto-planner)
- DuckDB postgres scanner: filter pushdown is a single experimental setting (`pg_experimental_filter_pushdown`, default true) — i.e., far cruder than Trino's per-connector pushdown framework — [DuckDB postgres docs](https://duckdb.org/docs/current/core_extensions/postgres/overview.html)
- MotherDuck's answer to the same problem is a per-query planner: "the optimizer decides, per query, whether parts run on the client or in the cloud", sending each query stage to a suitable location; queries touching cloud data run on the cloud engine which reads storage directly, and local↔cloud joins in one SQL statement are supported — [MotherDuck architecture docs](https://motherduck.com/docs/concepts/architecture-and-capabilities/)

### Inferences
- DuckDB's postgres scanner (from general knowledge of its implementation, consistent with the docs above): it pushes projections and simple comparison predicates, parallelizes reads via Postgres TID range scans / binary COPY, but any predicate it can't express (functions, LIKE patterns beyond its support, joins, aggregates) degrades to streaming the whole table through and filtering in DuckDB. On a large table behind a WAN link that is the cliff: a "SELECT sum(x) WHERE complex_pred" becomes a full-table network copy per query.
- Decision heuristic for the Alephgrid broker, synthesized from the above: (1) point lookups / highly selective simple predicates on an indexed source → federate live; (2) anything the spreadsheet will touch repeatedly (grid scrolling, formula recalc, agent iteration) → materialize into DuckDB once, serve all reads locally; (3) aggregations over big remote tables → either push the whole aggregation down as source-dialect SQL (ADBC/`postgres_query`-style raw pass-through, which sidesteps pushdown-expressiveness limits entirely) or run on a local materialization — never rely on scanner-level predicate pushdown for them; (4) writes → always pass through explicitly, never as a side effect.
- The "raw query pass-through" pattern (DuckDB's `postgres_query()` table function / Trino's `query` table function equivalent) is the pragmatic escape hatch: the mediator sends source-dialect SQL it composed itself, guaranteeing the heavy work runs at the source, and DuckDB only post-processes. A spreadsheet mediator can exploit this because it controls query generation, unlike a generic SQL federation engine that must handle arbitrary user SQL.
- An interactive spreadsheet amplifies the cliff: a grid re-render can trigger dozens of queries per minute, so "federate live" is only safe for small results; cached materialization (Q4) is not an optimization but the core architecture.

### Gaps
- No published quantitative benchmarks found this session for DuckDB postgres-scanner pushdown performance cliffs (e.g., full-table-pull measurements); the duckdb.org "Querying Postgres Tables Directly From DuckDB" blog post and community benchmarks should be pulled for numbers.
- Trino's own docs describe mechanics, not decision cost models; no public documentation found of how Trino *costs* pushdown vs local execution (largely rule-based, not cost-based, per general knowledge — unverified).

## Q4: Hybrid caching — materializing remote tables with freshness tracking and incremental refresh

### Takeaway
There is solid prior art for the storage half (MotherDuck's differential storage: append-only snapshot layers over object storage, snapshot IDs for consistent reads — now re-implemented openly by OpenDuck) and good primitives for freshness (DuckDB's postgres schema-cache staleness check via pg_class.xmin; Delta/Iceberg snapshot+time-travel semantics). The refresh half (CDC) is where tooling is thin in-process; dedicated movers (Sling, dlt) and later Debezium/wal2json are the realistic refresh engines, not DuckDB itself.

### Cited Findings
- MotherDuck differential storage: a logical database file is mapped onto append-only snapshot layers in cloud object storage; built because DuckDB's native single-writer file format doesn't suit concurrent multi-user access — [MotherDuck docs/blog via architecture pages](https://motherduck.com/docs/concepts/architecture-and-capabilities/)
- OpenDuck (third-party OSS) reimplements this: append-only sealed layers tracked in Postgres metadata, snapshot UUIDs for consistent reads, backed by local disk or S3-compatible storage — [OpenDuck listing](https://openapps.pro/apps/openduck)
- DuckDB's postgres extension already ships a freshness primitive: `pg_staleness_query_enabled` checks `pg_class.xmin` per table every query and auto-reloads cached schema metadata on change — a model for cheap source-side change probes — [DuckDB postgres docs](https://duckdb.org/docs/current/core_extensions/postgres/overview.html)
- Delta time travel is now supported by DuckDB's delta extension (May 2026), and catalog-managed-table writes are staged and registered through Unity Catalog before becoming visible — snapshot/version IDs are first-class freshness tokens for lakehouse sources — [DuckDB Delta/UC blog](https://duckdb.org/2026/05/07/delta-uc-updates.html)
- Sling (Go ELT tool) demonstrates the "extract database tables into DuckDB-managed storage" pattern, including extracting databases into DuckLake; its Delta Lake support runs on DuckDB's Delta reader and is read-only (extract-only) — [Sling blog: Delta Lake](https://blog.slingdata.io/efficient-data-lake-management-with-sling-and-delta-lake); [Sling blog: databases → DuckLake](https://blog.slingdata.io/tag/etl)
- dlt (Python, ELT library) pipelines writing API/database data into a DuckDB file, then querying it, is an established pattern (Kestra blueprint; Dagster example combining Sling for Postgres→DuckDB with dlt for GitHub API→DuckDB) — [Kestra blueprint](https://kestra.io/blueprints/dlt-duckdb-analytics-chain); [Dagster ELT example](https://docs.dagster.io/examples/full-pipelines/elt-pipeline)

### Inferences
- A workable Alephgrid caching design assembled from these parts: each connected remote table gets a local materialization (DuckDB native table or DuckLake table) plus a freshness record = {source snapshot token, fetched_at, row_count, content hash or max(updated_at)/max(pk)}. Source snapshot tokens by family: Iceberg/Delta snapshot or version id; HTTP sources ETag/Last-Modified (httpfs already deals in these); Postgres a cheap probe (xmin-style, max(updated_at), or pg_stat_user_tables counters); Sheets the Drive file's modifiedTime. Refresh = compare token, then incremental (append by watermark column) or full reload.
- DuckLake is the natural cache substrate for Alephgrid specifically: it gives snapshot isolation, time travel, and multi-reader semantics over Parquet + a SQL metadata catalog, so "refresh" becomes "new DuckLake snapshot" and spreadsheet sessions pin a snapshot id — the OpenDuck/MotherDuck layering without building custom storage. (Contingent on confirming DuckLake maturity, see Q1 gap.)
- CDC staging: start with batch incremental refresh (watermark columns / full reload on token change) because it needs nothing from the source beyond SELECT; add log-based CDC later via Debezium or wal2json only for sources that demand sub-minute freshness — both are JVM/external-process components, i.e., sidecars, consistent with the "Rust core, optional sidecars" constraint. No source retrieved this session documents a Rust-native, production-grade Postgres logical-decoding client; treat that as a gap.
- Sling is Go (single binary) and dlt is Python; either can be shelled out to as a refresh engine before Alephgrid grows its own incremental loader. Sling fits the sidecar constraint better (single static binary, config-file driven).

### Gaps
- No retrieved source on ETag-based caching patterns in DuckDB httpfs specifically (general knowledge says httpfs caches and supports range requests; verify on duckdb.org httpfs docs).
- Licensing check needed before bundling: Sling's license (repo shows source-available/Apache status has changed over time — unverified this session), dlt is Apache-2.0 per general knowledge (verify), Debezium Apache-2.0 (verify), OpenDuck license unknown.
- No published numbers found on incremental-refresh freshness/latency tradeoffs for DuckDB-backed caches.

## Q5: Credential brokering — per-source secrets server-side, short-lived creds, SSRF/connection-string hardening

### Takeaway
The BI-tool consensus is: credentials live only server-side (env vars or a secret manager), clients get opaque handles/tokens, and the historically exploited surface is not the secret store but the connection-configuration path itself — Metabase has a multi-year CVE trail (H2 connection strings → RCE, JDBC params → file read, Snowflake connection config → RCE, template evaluation → credential leak) proving that "user-supplied connection string" is the most dangerous input a mediator accepts. Alephgrid should treat connection configs as structured, allowlisted fields, never raw URIs/param bags.

### Cited Findings
- Metabase CVE-2023-38646: pre-auth RCE chained through the H2 database connection-string feature (setup token + H2 JDBC URL code execution) — the canonical cautionary tale for accepting connection strings — [Assetnote research writeup](https://www.assetnote.io/resources/research/chaining-our-way-to-pre-auth-rce-in-metabase-cve-2023-38646)
- Metabase CVE-2023-37470: H2 connection strings could carry code the server executes; mitigations included blocking POST /api/database, PUT /api/database/:id, POST /api/setup/validate at the network layer; the durable fix was migrating file-based H2 use to SQLite — [NVD entry](https://nvd.nist.gov/vuln/detail/CVE-2023-37470)
- Metabase CVE-2026-50147: a user who can configure a MySQL/MariaDB connection can add JDBC parameters that make the driver read files from the Metabase host; fixed in 1.57.19.1 / 1.58.14.1 / 1.59.10 / 1.60.4 — arbitrary driver params = local file read primitive — [SentinelOne vulnerability DB](https://www.sentinelone.com/vulnerability-database/cve-2026-50147/)
- Metabase (2026 advisories): a user who can add/edit a database connection could achieve RCE by configuring a Snowflake connection (affected from 1.54.0); and CVE-2026-59826, an authenticated admin could register an H2 connection via a code path that skipped validation (fixed 1.58.15.1 / 1.59.12 / 1.60.6.3 / 1.61.2) — validation bypasses recur even after the original fix — [Metabase CVE trackers](https://www.cvelogic.com/vendor/metabase); [exploit-intel vendor page](https://exploit-intel.com/vendor/metabase)
- Metabase Enterprise: low-privileged users could extract database credentials through email-template evaluation (fixed 0.57.13 / 0.58.7) — secrets leak through unrelated template/render features, not just the connection path — [releasealert Metabase CVE list](https://releasealert.dev/rubygems/metabase/cves)
- Cube: data-source settings come from `CUBEJS_`-prefixed environment variables; docs warn never to commit credential-bearing env vars to version control — i.e., Cube's model is "secrets are deployment config, never user data" — [Cube configuration docs](https://docs.cube.dev/configuration/overview)
- Clients of Cube authenticate with tokens generated from the deployment (REST API auth token), not database credentials — database secrets never transit to BI clients — [Slingshot docs on connecting Cube](https://www.slingshotapp.io/en/help/docs/analytics/datasources/supported-data-sources/cube.html); Vercel's Cube connector "requests Cube credentials only when your application or agent needs them instead of copying secrets into application code" — [Vercel Connect: Cube](https://vercel.com/connect/cube)
- General ingestion-tool practice (DataHub): reference environment variables or external vaults (AWS Secrets Manager, HashiCorp Vault) instead of plain-text passwords in recipes — [DataHub secret management](https://support.datahub.com/hc/en-us/articles/41912163768859-Ingestion-Recipe-Secret-Management)

### Inferences
- Concrete broker design for Alephgrid, derived from the CVE pattern + Cube model: (1) connections are rows in a server-side store, created from *structured fields* (host, port, db, user, TLS mode) with per-driver allowlists of extra options — never a raw URI, never a free-form parameter map (every Metabase file-read/RCE above rode a free-form param or embedded-engine URI); (2) secrets encrypted at rest (or delegated to a vault), returned to no API response; clients and AI agents reference connections by id and interact only through query endpoints; (3) DuckDB secrets are created per-request in-memory from the broker (DuckDB's `CREATE SECRET` is session-scoped by default), so even SQL-level users can't `SELECT * FROM duckdb_secrets()` a persisted credential — note duckdb_secrets() redacts but the safest posture is non-persistent secrets per attached session.
- SSRF controls for user-supplied hosts (standard practice, not from a retrieved source — verify against OWASP SSRF cheat sheet when writing the doc): resolve the hostname, reject private/link-local/metadata ranges (RFC1918, 169.254.169.254, ::1) unless the deployment explicitly allowlists them; re-check after redirects for HTTP sources; pin DNS resolution to connect time to beat DNS-rebinding; run source-facing connections from a network-segmented egress. For httpfs/gsheets-style URL sources this matters as much as for DB hosts.
- Short-lived credentials map cleanly per source family: Postgres/MySQL via IAM auth tokens (RDS/CloudSQL) or Vault dynamic DB credentials; Snowflake via key-pair JWT or OAuth; BigQuery/Sheets via OAuth refresh-token → short-lived access token minted server-side (which is exactly what the gsheets extension's `access_token` provider consumes). The broker owns refresh; executors only ever see ≤1h tokens.
- The embedded-engine lesson (H2 CVEs) applies directly to DuckDB: Alephgrid must never let users ATTACH arbitrary local paths or install arbitrary extensions through connection config — DuckDB's own hardening knobs (`enable_external_access=false` where applicable, `allowed_paths`/`allowed_directories`, `lock_configuration`, disabling community extensions per Q1) are the equivalent mitigations (knob names from general knowledge; verify on the Securing DuckDB pages, same doc tree as the cited securing_extensions page).

### Gaps
- Hex's and Preset's credential-management specifics did not surface in results (Preset/Superset encrypts connection secrets in its metadata DB per general knowledge — unverified); their docs should be fetched directly if needed.
- No retrieved source describing a classic SSRF (internal-network request forgery) in Metabase's connection feature specifically — the CVE trail is file-read/RCE/credential-leak; SSRF guidance above is standard practice rather than cited incident.
- Metabase advisory version numbers conflict slightly across the aggregator sources cited; confirm against official Metabase security advisories before quoting exact versions externally.

## Q6: Prior art — DuckDB-powered mediators and universal query layers; the open niche

### Takeaway
The prior art splits into: cloud-DuckDB platforms (MotherDuck — dual execution + differential storage, proprietary; OpenDuck re-implementing it openly), heavyweight federation engines (Trino: JVM, operates fleets of connectors; DataFusion: the Rust toolkit), movers (Sling, dlt), and a cautionary tale (GlareDB: DataFusion-based hybrid-execution Postgres-compatible federator that threw away its engine for a rewrite and dropped external-system support; third-party sources now describe it as pivoted/abandoned). Nobody occupies "spreadsheet-shaped, agent-first, open-source mediator with DuckDB as the compute cache" — the federation engines have no UI/agent surface, the BI tools don't write back or expose a programmatic grid, and the DuckDB clouds are proprietary services.

### Cited Findings
- MotherDuck: dual execution (per-query-stage placement between client DuckDB and cloud engine; local↔cloud joins in one statement; formerly "Hybrid Execution") and differential storage (append-only snapshot layers over object storage) are its two architectural pillars; proprietary service — [MotherDuck architecture docs](https://motherduck.com/docs/concepts/architecture-and-capabilities/); [dual-execution video/page](https://motherduck.com/videos/bringing-duckdb-to-the-cloud-dual-execution-explained/)
- OpenDuck: third-party open reimplementation of both ideas (sealed append-only layers, Postgres-tracked metadata, snapshot UUIDs, S3-compatible backing) — evidence the architecture is replicable outside MotherDuck — [OpenDuck listing](https://openapps.pro/apps/openduck)
- GlareDB: GitHub main branch holds a work-in-progress new engine (earlier called "rayexec", developed in a separate glaredb_next repo); the DataFusion-based code lives in a legacy branch; support for external systems like BigQuery and Postgres was "temporarily removed" in the move; README says the new engine is "still a bit aways from being production ready" — [GlareDB/glaredb GitHub](https://github.com/GlareDB/glaredb); [blog coverage of the engine swap](https://www.plushcap.com/content/glaredb/blog/glaredb-glaredb-is-getting-a-whole-new-engine)
- GlareDB status conflict: dbdb.io states the company pivoted to an AI startup in 2025 and the project "was last updated in November 2025 and has since been abandoned"; this conflicts with the repo README's framing and is unverified — [dbdb.io GlareDB entry](https://dbdb.io/db/glaredb); in its DataFusion era, GlareDB shipped hybrid execution and Iceberg support, explicitly following MotherDuck's model — [Hackernoon: what the heck is GlareDB](https://hackernoon.com/what-the-heck-is-glaredb)
- DataFusion: extensible Rust query engine ("toolbox" positioning per its user guide) — the main Rust-native alternative substrate to DuckDB for building a federator — [DataFusion introduction](https://datafusion.apache.org/user-guide/introduction.html)
- Trino: mature connector-pushdown framework with per-connector capability matrices and EXPLAIN-visible pushdown (see Q3 citations) — the reference design for connector capability modeling — [Trino pushdown docs](https://trino.io/docs/current/optimizer/pushdown.html)
- BoilingData: 2023 writeup of distributing DuckDB across AWS Lambda functions for fast aggregations; nothing found on current status/product — likely dormant as a mediator precedent — [BoilingData Medium post](https://boilingdata.medium.com/lightning-fast-aggregations-by-distributing-duckdb-across-aws-lambda-functions-e4775931ab04)
- Sling: Go ELT tool, loads databases into DuckDB/DuckLake/Delta (Delta read-only, via DuckDB's reader) — mover, not mediator — [Sling blog](https://blog.slingdata.io/efficient-data-lake-management-with-sling-and-delta-lake)
- dlt: Python ELT library routinely paired with DuckDB as destination (Kestra/Dagster examples) — mover, not mediator; Python-only so sidecar-tier for Alephgrid — [Kestra blueprint](https://kestra.io/blueprints/dlt-duckdb-analytics-chain); [Dagster example](https://docs.dagster.io/examples/full-pipelines/elt-pipeline)

### Inferences
- GlareDB's arc is the key strategic lesson: it built almost exactly Alephgrid's proposed broker (DataFusion core, Postgres/BigQuery/Snowflake external tables, hybrid local/cloud execution) and still rewrote the engine and shed the connectors — suggesting (a) maintaining N native connectors on a general-purpose engine is a treadmill, and (b) betting on DuckDB's *existing, DuckDB-team-maintained* scanner ecosystem (Q1) rather than writing connectors is the defensible position for a small OSS team. Alephgrid's connector broker should be a thin orchestration/credential/caching layer over DuckDB extensions + ADBC, not a connector framework of its own.
- Evidence.dev's use of duckdb-wasm for in-browser SQL is part of this landscape per general knowledge (static-site BI, queries run client-side on pre-built parquet); it did not surface in this session's results — verify at evidence.dev docs if cited. Its relevance: precedent for shipping DuckDB-computed results to a web grid cheaply.
- The open niche, stated concretely: (1) a spreadsheet/grid as the query surface rather than SQL-first dashboards; (2) write-back to sources (DuckDB's postgres/mysql/iceberg/delta write support makes two-way sync feasible — BI tools are read-only); (3) agent-first API where an AI agent gets connection *handles* + schema + query endpoints but never credentials (Q5); (4) local-first/self-hostable, vs MotherDuck/BoilingData being cloud services; (5) freshness-tracked materialization as a first-class concept (Q4) rather than Trino-style always-live federation.
- Rust-specific note: DuckDB embeds in Rust via the duckdb-rs crate (general knowledge; MIT like DuckDB itself — verify crate license), so the whole Tier-1 connector surface is reachable from the existing axum process with zero sidecars; ADBC (Q2) and movers (Sling binary, dlt sidecar) extend the long tail.
