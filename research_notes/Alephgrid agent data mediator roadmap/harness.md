# Agent Data Harness Patterns for Alephgrid (layer above identity/gateway)

Research date: 2026-10-31. Scope: how 2025–2026 agent↔data products structure tooling, context, and evaluation so agents answer correctly and cheaply, and which open-source pieces Alephgrid should adopt or interoperate with. (Authorization/sandboxing deliberately excluded per prior research.)

## Q1. Agent-to-database tooling patterns and tool granularity (raw SQL vs typed plans vs metric queries), with eval evidence

### Takeaway
The late-2026 consensus converges on a spectrum, not a single answer: governed/constrained SQL against curated views in the middle beats both raw warehouse SQL (hallucinated joins, ungoverned logic) and rigid JSON/plan formats (too inflexible); metric-registry queries win decisively **within their modeled scope** (dbt measured 98–100% vs 84–90% for text-to-SQL on the same questions) but fail hard (0%) outside it. Real-enterprise benchmarks (Spider 2.0) show raw text-to-SQL agents remain far from solved on 1,000+-column schemas, which is the strongest published evidence for mediated/semantic tool shapes.

### Cited Findings
**Tool shapes of shipping MCP servers**
- Snowflake's managed MCP server is a native Snowflake object assembled tool-by-tool via `CREATE MCP SERVER` (max 50 tools): tool types include Cortex Analyst (semantic-model NL query), Cortex Search, a SQL execution tool that is `read_only: true` by default, and a generic stored-procedure wrapper; RBAC applies per-server and per-tool — [Snowflake docs (Cortex Agents MCP)](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-mcp); roundup at [Bytebase](https://www.bytebase.com/blog/top-open-source-multi-database-mcp-servers/)
- For Postgres, the de facto official servers are Supabase (true read-only mode, per-project scoping) and Neon (branching + "safe migration" workflow); self-managed options are Postgres MCP Pro (restricted mode) and DBHub — [SaturnSQL roundup](https://saturnsql.com/blog/best-mcp-servers-for-databases), [Coworker roundup](https://coworker.ai/blog/best-mcp-servers-for-databases) (vendor/affiliate-style roundups; I did not verify each official doc)
- Google's MCP Toolbox for Databases (open source, multi-engine incl. Postgres and Snowflake) is configured from a file of **named, parameterized queries** instead of handing the agent raw SQL; includes auth gating and OpenTelemetry — [Bruin roundup](https://getbruin.com/blog/data-tools-with-mcp-servers-2026/)
- Bytebase's MCP server inherits the permissions of the identity the agent authenticates as, so a prompt cannot widen access — [Bytebase](https://www.bytebase.com/blog/top-open-source-multi-database-mcp-servers/)
- MotherDuck's `mcp-server-motherduck` (local MCP server for DuckDB and MotherDuck) is MIT-licensed, 536 stars, actively pushed as of 2026-10-26 — verified via GitHub API (repos/motherduckdb/mcp-server-motherduck)
- dbt's MCP server exposes semantic-layer tools: `list_metrics`, `get_dimensions`, `get_entities`, `get_dimension_values`, `query_metrics` (filter/group/sort), `get_metrics_compiled_sql` (returns compiled SQL without running), plus discovery and dbt-CLI tool groups; exact tool set varies by version — [dbt MCP available tools](https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools), [dbt-mcp on PyPI](https://pypi.org/project/dbt-mcp/2.3.1/)
- Databricks Genie's accuracy levers are all context/curation, not model: table+column descriptions, column synonyms, **sampled values and value dictionaries**, plain-text "instructions" (business rules, terminology, date formats), an example-SQL library, and "trusted assets" — parameterized verified queries/SQL functions; a response is marked *trusted* only when the exact text of a verified parameterized query or SQL function produced it — [Databricks Genie trusted assets](https://docs.databricks.com/genie/trusted-assets.html), [Genie concepts](https://docs.databricks.com/aws/en/genie/concepts)
- Cube (D3, renamed "Cube Agentic Analytics" at GA) made a deliberate granularity choice: the agent writes **"Semantic SQL" against governed views** — flexible SQL, but only over governed measures/dimensions, so metric logic, joins, and permissions are enforced by the semantic layer rather than the prompt; a linter rejects invalid constructs before execution; they explicitly chose this over a rigid JSON query format — [Cube: Building an agentic analytics harness](https://cube.dev/blog/building-an-agentic-analytics-harness)

**Accuracy evidence**
- dbt Labs 2026 benchmark (ACME Insurance 15-table 3NF schema, 11 questions × 20 runs, Pydantic AI + DuckDB; code published at github.com/dbt-labs/dbt-llm-sl-bench): with minimal modeling, claude-sonnet-4-6 scored 90.0% text-to-SQL vs 98.2% semantic layer; gpt-5.3-codex 84.1% vs 100.0%. On the raw schema, 2026 scores were 64.5% (text-to-SQL) vs 72.7% (semantic layer), up from 32.7%/60.5% with GPT-4 in 2023. Questions outside the modeled scope scored **0%** on the semantic layer (it errors rather than answers) — [dbt: Semantic Layer vs Text-to-SQL 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026). Caveats stated by the authors: full-schema context flatters text-to-SQL and is unrealistic at scale; 11 questions, one dataset; vendor-authored.
- Spider 2.0 (632 real-world text-to-SQL workflow problems; databases often >1,000 columns; BigQuery/Snowflake/SQLite/DuckDB): original 2024 baselines were ~10–27% (GPT-4o 10.1%, o1-preview 17.1%, Claude-4-Sonnet ~26–28% via Spider-Agent). Leaderboard as of late Oct 2026: top agents reach 96.70 on Spider 2.0-Snow, 76.23 on Spider 2.0-Lite, but only **65.6 on Spider 2.0-DBT** (repository-level DuckDB/dbt task, 68 examples) — [spider2-sql.github.io](https://spider2-sql.github.io/)
- BIRD: top system 82.95 execution accuracy (GrainSQL, Sep 2026) vs human baseline 92.96 — [count.co text-to-SQL review](https://count.co/ai/text-to-sql) (secondary source; official leaderboard not fetched directly)
- Benchmark health warning: a VLDB/CIDR 2026 paper reports annotation error rates of **52.8% for BIRD Mini-Dev and 66.1% for Spider 2.0-Snow**, meaning leaderboard numbers may substantially overstate real accuracy — [Pervasive Annotation Errors Break Text-to-SQL Benchmarks](https://arxiv.org/pdf/2601.08778), [CIDR 2026 paper](https://www.vldb.org/cidrdb/papers/2026/p5-jin.pdf)
- Semantic-layer accuracy evidence is almost entirely dbt-authored; no independent head-to-head eval of dbt MCP vs Cube vs Cortex Analyst was found. A Promethium page cites a conflicting "83% vs ~40%" figure attributed to dbt internal testing that I could not trace to an original — [Promethium comparison](https://promethium.ai/guides/top-10-semantic-layer-tools-2026-definitive-comparison/)

### Inferences
- Alephgrid's prior conclusions (read-only gateway + small metric registry + typed plans) match the field, but the evidence suggests a **three-tier tool surface** is the winning shape: (1) metric/registry queries for governed questions (highest accuracy, deterministic SQL generation à la MetricFlow), (2) constrained/linted SQL over curated views for exploration (Cube's choice; avoids the 0%-outside-scope cliff), (3) raw SQL only as an audited escape hatch. The semantic layer's hard failure mode (error, not wrong number) is itself a feature worth copying: "refuse outside scope" beats "plausible wrong answer."
- Databricks' "trusted assets" and Snowflake's "verified queries" are the same pattern: a store of human-verified parameterized queries that the agent prefers and that mark responses as trusted. This maps directly onto Alephgrid's ResultHandle/answer-receipt concept — a receipt can carry a "trusted: derived from verified query X" flag cheaply.
- Spider 2.0-DBT (DuckDB, 65.6% ceiling) is the single most relevant public benchmark for Alephgrid (DuckDB engine, workflow-level tasks) and is worth adopting as an internal eval target.

### Gaps
- No independent (non-vendor) eval comparing metric-query tools vs constrained SQL vs raw SQL on the same workload. dbt's is the only controlled comparison and is vendor-run.
- Could not confirm current official BIRD/Spider leaderboard numbers beyond the Spider 2.0 site itself; BIRD figure is from a secondary blog.
- Exact MCP tool schemas for Snowflake's SQL-exec tool and Cortex Analyst were not fetched from primary docs (German-locale doc page surfaced; summarized via roundups).

## Q2. Context engineering for data agents: schema cards, dictionaries, profiling summaries — and measured impact

### Takeaway
Every serious product (Genie, Cortex Analyst, Cube, dbt) now treats curated context — descriptions, synonyms, sample values, verified queries, business instructions — as the main accuracy lever. Measured gains exist but are model-dependent: MotherDuck's study shows query-log-derived schema descriptions added up to +16 points execution accuracy for Gemini 2.5 Flash on their real warehouse, while the *same context hurt* a smaller model (Qwen 2.5-32B, −8 to −10 points). "Schema + sample values" is the strongest cheap baseline (+6–8 points over schema-only in the same study). No study isolating full profiling stats (cardinality/null rates) was found.

### Cited Findings
- MotherDuck research (query-log-informed schema descriptions): on BIRD-Dev, schema-only baseline 34.8% (Gemini 2.5 Flash) / 20.2% (Qwen 2.5-32B); **schema + sample values 42.2% / 28.2%** (i.e. samples alone worth ~+7 points); + query-annotation descriptions 38.0% Gemini (+3.2) but 19.4% Qwen (−0.8). On MDW-AMBIG (MotherDuck's production warehouse): schema-only 36% Gemini; + query-pattern descriptions **52% (+16)**; Qwen dropped from 18% to 8% with the same context. Authors attribute Qwen's drops to added context overwhelming a smaller model — [MotherDuck research page](https://motherduck.com/research/query-log-informed-schema-descriptions-text-to-sql/)
- A report cites work finding column descriptions raise accuracy by **over 20% on columns with uninformative names** (cited secondhand; original not confirmed) — [dev.to summary](https://dev.to/omer_hochman/your-text-to-sql-accuracy-is-measured-on-schemas-your-users-will-never-build-32b2)
- Corral Data 2025 study tested combinations of seven metadata types (table/column descriptions, FKs, etc.); snippets show ~60% accuracy for both schema-only and column-description configs but full deltas not retrieved — [Corral Data PDF](https://corraldata.com/wp-content/uploads/2025/01/PriceCorralData2025_MetadataTextSQL.pdf)
- Databricks Genie's documented context inputs: table/column metadata descriptions, column-level synonyms, **sampled values and value dictionaries**, plain-text instructions (business rules, terminology, date formats), example-SQL library, trusted assets; benchmarks are eval-only (never fed back as context) — [Genie concepts](https://learn.microsoft.com/azure/databricks/genie-agents/concepts), [trusted assets](https://docs.databricks.com/genie/trusted-assets.html)
- Snowflake Cortex Analyst accuracy guidance: verified ("gold") queries, usage-based suggestions, and custom NL instructions attached to semantic views — [Snowflake docs: improving accuracy](https://docs.snowflake.com/user-guide/views-semantic/improving-accuracy)
- Cube's harness separates business context by owner and loading rule: semantic metadata, free-form Markdown business docs, certified queries (loaded **only when relevant**), MCP connectors to wikis, and memory (corrections from earlier runs, scoped carefully because one team's correction can mislead another). Its `searchDataModel` tool refreshes + searches the model, filters by caller's access, and returns a compact candidate set **instead of preloading the whole model** — [Cube harness post](https://cube.dev/blog/building-an-agentic-analytics-harness)
- dbt's benchmark note: giving the agent the full schema as context "is impractical for larger datasets" — schema retrieval/search is required at scale — [dbt 2026 benchmark](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)

### Inferences
- For Alephgrid: auto-generated **schema cards = DDL + 3–5 sample values per column + row count** is the evidence-backed cheap default (sample values have the clearest measured gain). Human/agent-authored descriptions and synonyms should be a first-class, versioned artifact (Alephgrid can store them in the workbook/catalog), and a query-log-mining job that proposes descriptions (MotherDuck's approach) is a differentiating feature a mediator is uniquely positioned to run, since it sees all queries.
- Context should be served through a search tool (`search_catalog` returning compact candidates), not preloaded — both Cube and dbt converge on this; it also keeps context proportional to task and respects per-caller visibility.
- Context volume is not monotonic: the Qwen regression is a warning that harnesses serving multiple/smaller models need per-model context budgets, not one fat prompt.

### Gaps
- No published study isolating profiling statistics (cardinality, null rates, min/max) as the variable; MotherDuck mentions profiling-stat baselines but numbers for that condition were not in the fetched page. The "10–20% accuracy from basic table/column stats" figure found is an unverified vendor claim ([Promethium](https://promethium.ai/guides/enterprise-text-to-sql-accuracy-benchmarks-2/)).
- No published numbers on how much Genie's sample values / value dictionaries or Cortex verified queries improve accuracy.

## Q3. Efficiency: token/cost patterns — previews + handles, pagination, sampling, caching of analysis artifacts

### Takeaway
The field has converged on exactly the pattern Alephgrid already planned (ResultHandle): return a token-bounded preview + total count + an opaque handle; keep full results out of model context (file/resource the agent can query, or code execution over the data). Naive per-page pagination through the context window is increasingly considered an anti-pattern for large results.

### Cited Findings
- Cube's production harness: query results return **the first 100 rows, the total row count, a query ID for fetching more, and a truncation flag** (so the agent never presents a sample as a total); runtime errors return recovery hints (e.g., "retry identifier in quotes", "retry with longer timeout"), which they report reduces repeated bad calls; separate sub-agents handle dashboard building and model changes to keep the main thread lean; model changes persist as commits on a dev branch so later runs continue the work — [Cube harness post](https://cube.dev/blog/building-an-agentic-analytics-harness)
- Anthropic's "code execution with MCP": agents filter/transform tool results in code before returning them; intermediate results stay in the execution environment by default rather than entering model context — [Anthropic research post](https://www.anthropic.com/research/code-execution-with-mcp)
- Superglue built pagination for MCP tool results, then deleted it: at a 20 KB page budget, 12.4 MB of data needs ≥620 calls; their conclusion: "Big results belong in a file the agent can query, not in the prompt." They note the MCP spec recommends opaque handles for state spanning calls, and defines cursor pagination only for list operations (tool-result pagination proposal still pending) — [superglue blog](https://superglue.ai/blog/mcp-tool-result-limits/)
- Runpod's MCP tool design guidance: return a resource URI the agent can fetch on demand instead of embedding the payload — [Runpod](https://www.runpod.io/blog/designing-mcp-tools); FutureSearch proposes a token-bounded preview with pagination hints while full data flows to the client out-of-band via `structuredContent` — [FutureSearch](https://futuresearch.ai/blog/mcp-results-widget/)
- Datadog's MCP server team: entire tool results land in the context window and observability data is large; fix is letting agents query for only what they need — [Datadog engineering](https://www.datadoghq.com/blog/engineering/mcp-server-agent-tools)
- Other guides still recommend `nextCursor`/`has_more` pagination plus field filtering, so the ecosystem is not fully reconciled — [MindStudio](https://www.mindstudio.ai/blog/reduce-token-usage-ai-agents-mcp-optimization), [ChatForest pagination patterns](https://chatforest.com/guides/mcp-pagination-patterns/)
- dbt's `get_metrics_compiled_sql` (return the SQL, don't run it) is a cheap "plan preview" tool shape — [dbt-mcp PyPI](https://pypi.org/project/dbt-mcp/2.3.1/)
- Caching of agent analysis artifacts: Cube persists memory (corrections/decisions that return when applicable) and certified queries loaded only when relevant; Genie's query library and trusted assets act as a reusable verified-answer cache — [Cube harness](https://cube.dev/blog/building-an-agentic-analytics-harness), [Genie trusted assets](https://docs.databricks.com/genie/trusted-assets.html)

### Inferences
- Alephgrid's ResultHandle should carry: N-row preview (≈100 rows is the field's number), total row count, truncation flag, and a handle usable by follow-up tools (`fetch_rows(handle, offset, limit)`, `aggregate(handle, …)`, `sample(handle, n, method)`) — and since Alephgrid *is* a DuckDB compute engine, the "file the agent can query" is naturally a snapshot-pinned temp table/view behind the handle; this is a structural advantage over pass-through MCP servers.
- Error messages with recovery hints are a measurable efficiency lever (fewer retry loops) and cheap to implement in the gateway.
- The verified-query store (Q1/Q2) doubles as the artifact cache: a successful agent analysis promoted to a named, parameterized verified query is both an accuracy and a cost optimization (skip regeneration entirely).

### Gaps
- No published quantitative token/cost savings numbers (e.g., "% tokens saved by handles vs inline") from any vendor; all evidence is design rationale and operational anecdote.

## Q4. The spreadsheet angle: products where agents and humans share one artifact

### Takeaway
Quadratic was the closest open-source comparable (Rust/WASM grid + AI that writes code/SQL into cells) but went closed-source around March 2026 and its canonical repo is gone, leaving the "open-source AI-native spreadsheet with SQL connections" slot effectively vacant — a direct opening for Alephgrid. The Excel-native agents (Shortcut, Paradigm) score at best ~59–75% on independent-ish benchmarks and are criticized for reliability, indicating the human+agent shared-grid problem is far from solved.

### Cited Findings
- Quadratic: built with Rust compiled to WASM + WebGL canvas; its AI wrote Python that ran in the sheet, fed output back to the model for debugging, and generated data onto the grid using sheet context ("knows the context of your document, your code, the output") — [HN Show HN](https://news.ycombinator.com/item?id=35456509). Its docs say it was released under a **source-available license, not open source** ("free to hobbyists… retaining rights to charge enterprises") — [Quadratic docs: source available](https://docs.quadratichq.com/company/quadratic-is-source-available); a note on a Quadratic-hosted post says "as of March 2026, Quadratic is now closed-source" — [Quadratic blog](https://www.quadratichq.com/blog/comparing-the-5-best-open-source-spreadsheets). Verified directly: `github.com/quadratichq/quadratic` now returns 404 via GitHub API; only community mirrors survive, incl. `AyushAgrawal-A2/quadratic` described as "Spreadsheet with AI, Code, Connections (last public snapshot)" (GitHub search, 2026-10). So the original design can still be studied from the snapshot mirror, but it is not a licensing-safe code source and no longer an open-source competitor.
- Shortcut.ai (Fundamental Research Labs): claims SOTA 59.25% verified on SpreadsheetBench — but the benchmark "was developed in collaboration with Shortcut.AI," i.e., creators have a stake — [Shortcut blog](https://shortcut.ai/blog/posts/spreadsheetbench), [SpreadsheetBench repo](https://github.com/RUCKBReasoning/SpreadsheetBench); claims Wall Street Prep ranked it #1 at 5.9/10 vs Claude 5.5, Copilot 4.4, ChatGPT 2.5 (vendor-reported only) — [Shortcut blog](https://shortcut.ai/blog/posts/wsp-ranked-1); claims it beats first-year analysts 89.1% in a blind study (self-published, unverified) — [Shortcut blog](https://shortcut.ai/blog/posts/analyst-benchmark)
- Paradigm: in AIMultiple's independent "Top 15 AI Excel Tools Benchmarked," Paradigm reached ~75% accuracy but "the AI chat did not work consistently" — reviewer had to re-ask questions several times — [AIMultiple](https://aimultiple.com/ai-excel)
- A newer OSS project (GridOS) takes an explicitly mediated approach: the LLM handles intent/routing/structuring but is "physically blocked from writing directly to the cells"; every response goes through a collision-checked, lock-aware preview step guarded by a strict Python AST backend; core MIT-licensed per the author — [dev.to post](https://dev.to/shreydevkar/i-built-an-open-source-ai-spreadsheet-that-doesnt-hallucinate-math-25g8) (single-author claim, small project)
- SpreadsheetBench itself: real-world spreadsheet-manipulation benchmark (912 questions from Excel forums, multi-round evaluation) — [GitHub](https://github.com/RUCKBReasoning/SpreadsheetBench)
- Hex (notebook/BI, not spreadsheet, but adjacent): rebuilt its product as "Hex 4.0, an agent-native system built on plain code rather than retrofitted AI" per HN digest coverage, Oct 2026 — [HN digest](https://zeli.app/digest/2026-10-27)

### Inferences
- What the spreadsheet agents get right: code-as-the-agent-action (Python/formulas into cells, output fed back for self-debugging — Quadratic), and benchmarking against real workbook tasks (SpreadsheetBench). What they get wrong per reviews: reliability/consistency (Paradigm), unverifiable self-benchmarks (Shortcut), and — in Quadratic's case — a business model that abandoned open source, which is Alephgrid's wedge.
- GridOS's "agent proposes, mediated preview applies" is independent convergence on Alephgrid's proposal-first mutation design — evidence the pattern resonates with users burned by agents overwriting grids.
- Best scores on realistic spreadsheet manipulation (~59%) are far below text-to-SQL-on-semantic-layer scores (~98%), suggesting Alephgrid should route agent work through its structured tools (SQL workspace, metric queries) rather than free-form grid editing wherever possible, and treat direct grid mutation as the hardest, most proposal-gated path.

### Gaps
- No public post-mortem or review of Quadratic's agent internals beyond early coverage; the last-snapshot mirror would need direct code reading (not done here).
- Paradigm's own published benchmarks not found; no independent head-to-head of Shortcut vs Paradigm.
- Wall Street Prep's original ranking page not verified (only Shortcut's account of it).

## Q5. Harness/eval infrastructure worth reusing

### Takeaway
Reusable OSS exists for all three eval layers: text-to-SQL accuracy (Spider 2.0 — esp. the DuckDB-based Spider 2.0-DBT split — and BIRD, with the caveat of high annotation-error rates), spreadsheet manipulation (SpreadsheetBench), and injection resistance (AgentDojo and successors; no SQL-specific suite exists, so Alephgrid would adapt one). dbt published its semantic-layer benchmark code, giving a ready template for metric-tool evals.

### Cited Findings
- Spider 2.0: 632 real-world workflow problems; **Spider 2.0-DBT split uses DuckDB** and is a repository-level agent task (top score only 65.6) — most relevant to Alephgrid — [spider2-sql.github.io](https://spider2-sql.github.io/)
- BIRD: execution-accuracy benchmark, human baseline 92.96 — [count.co](https://count.co/ai/text-to-sql); **but** annotation error rates measured at 52.8% (BIRD Mini-Dev) and 66.1% (Spider 2.0-Snow) — treat absolute scores skeptically, use relative deltas — [arXiv 2601.08778](https://arxiv.org/pdf/2601.08778), [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p5-jin.pdf)
- dbt's benchmark harness is published: github.com/dbt-labs/dbt-llm-sl-bench (Pydantic AI, DuckDB result storage, 11 questions × 20 runs methodology) plus github.com/dbt-labs/dbt-agent-skills — [dbt 2026 benchmark](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)
- SpreadsheetBench: 912 real-user spreadsheet manipulation questions, OnlineJudge-style eval — [GitHub](https://github.com/RUCKBReasoning/SpreadsheetBench)
- Injection-resistance suites (none SQL-specific): **AgentDojo** — 97 realistic user tasks, 629 security test cases; banking suite (11 tools, 16 user tasks, 9 injection tasks) is closest to data access; maintained in UK AISI's inspect_evals — [AgentDojo in inspect_evals](https://ukgovernmentbeis.github.io/inspect_evals/evals/agentdojo/index.html); **InjecAgent** — 1,054 cases, 17 user tools, 62 attacker tools — [GitHub](https://github.com/uiuc-kang-lab/InjecAgent); **AgentSec-Bench** — 240 tasks, 6 tool environments, 6 attack classes (incl. data exfiltration, unauthorized tool invocation), 3 obfuscation levels — [GitHub](https://github.com/drsafavi/agentsec-bench); AgentDyn extends AgentDojo with 560 injection cases — [GitHub](https://github.com/SaFo-Lab/AgentDyn)
- Cube's position on eval infra: agents need regression-test suites "you run on every change," and a grounded-answer test = real question + right number + asker's permissions + traceability to the producing definition — no methodology details published — [Cube Evals](https://cube.dev/blog/introducing-cube-evals)
- Databricks Genie has a built-in "benchmarks" feature: question/SQL pairs used strictly for evaluation, never fed back as context — [Genie concepts](https://docs.databricks.com/aws/en/genie/concepts)
- Synthetic data generators for text-to-SQL eval: no widely-adopted standalone OSS generator surfaced in this research; SM3-Text-to-Query is a synthetic multi-model medical benchmark (narrow domain) — [arXiv](https://arxiv.org/pdf/2411.05521)

### Inferences
- Concrete reuse list for Alephgrid: (1) Spider 2.0-DBT as the external accuracy yardstick (DuckDB-native); (2) dbt-llm-sl-bench as the template for metric-registry-vs-SQL internal evals; (3) SpreadsheetBench for grid-manipulation tools; (4) AgentDojo's harness pattern (utility + security measured together) with a custom DuckDB tool environment containing injected strings in query results — the "injection via data values returned from SQL" scenario is unserved by any existing suite and would be a credible OSS contribution that markets Alephgrid.
- Genie's "benchmarks are eval-only, never context" separation is a governance rule worth encoding: keep the verified-query store (context) and the eval set (grading) as distinct, non-overlapping artifacts to avoid training-on-test contamination of your own harness.

### Gaps
- No SQL-/warehouse-specific prompt-injection benchmark exists (confirmed absence across multiple searches) — gap and opportunity.
- No mature OSS synthetic data generator for text-to-SQL eval surfaced; may exist under other names (not found in this pass).

## Q6. Where a self-hosted open-source mediator fits vs SaaS; user complaints

### Takeaway
Direct evidence is thin (no single HN/Reddit thread crisply lists warehouse-agent complaints), but the pattern across threads is consistent: privacy/data-leaving-the-building is the stated reason users want self-hosted agents, reliability is the top complaint against shipped agent products, and every serious competitor in this space (Genie, Cortex Analyst, Cube D3, dbt Cloud SL, Shortcut, Paradigm, now Quadratic) is SaaS or closed — a self-hosted single-binary governed mediator has no direct open-source competitor identified in this research.

### Cited Findings
- HN discussions repeatedly push self-hosted agents on privacy grounds — e.g., a commenter won't use a cloud-hosted personal agent "until there's a solution that covers… personal data privacy"; a hybrid "local executor + cloud brain" design is proposed — [HN: Moltworker self-hosted agent](https://news.ycombinator.com/item?id=46810828)
- HN thread on production agents: users have "a fuzzy approximation" of what they want from a data warehouse, and the recurring complaint is agent reliability — [HN: What makes 5% of AI agents work in production?](https://news.ycombinator.com/item?id=45456381); see also [HN: Less capability, more reliability, please](https://news.ycombinator.com/item?id=43535653)
- Independent reviewer on Paradigm: ~75% accuracy but "the AI chat did not work consistently" — reliability over raw capability again — [AIMultiple](https://aimultiple.com/ai-excel)
- Quadratic abandoned open source (March 2026 closed-source note; repo 404) — the previously most-cited "open-source AI spreadsheet" is no longer one — [Quadratic blog note](https://www.quadratichq.com/blog/comparing-the-5-best-open-source-spreadsheets), GitHub API verification
- Open-source building blocks that do exist are infrastructure, not mediators: Google MCP Toolbox for Databases (config-file-defined parameterized query tools, OTel) — [Bruin](https://getbruin.com/blog/data-tools-with-mcp-servers-2026/); MotherDuck/DuckDB MCP server (MIT) — GitHub API; Bytebase MCP (identity-scoped) — [Bytebase](https://www.bytebase.com/blog/top-open-source-multi-database-mcp-servers/)
- Snowflake warns that using multiple third-party MCP servers risks tool poisoning/tool shadowing and recommends reviewing servers before use — trust in the MCP supply chain is an acknowledged vendor-level problem — [Snowflake docs via roundups](https://www.bytebase.com/blog/top-open-source-multi-database-mcp-servers/)

### Inferences
