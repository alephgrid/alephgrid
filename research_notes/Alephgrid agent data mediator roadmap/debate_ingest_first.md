# Debate Position: Ingest-First (Local-Engine-First) for Alephgrid

Position argued: Alephgrid should copy/sync data into its own DuckDB-managed storage (per-workbook DBs, Parquet, later DuckLake) and run all computation locally. External connections exist primarily as import/sync pipelines, not live query targets.

Context assumed: Alephgrid is a self-hosted OSS Rust/axum server with embedded DuckDB, serving a spreadsheet grid UI, and positioning itself as a mediator between AI agents, users, and data sources. Current as of late 2026.

---

## Why does local-engine execution win for a spreadsheet UI and agent mediator?

### Takeaway
A spreadsheet is the most latency-intolerant analytical UI that exists — every scroll, filter, and formula edit is a query — and DuckDB on local storage is demonstrably the fastest single-node engine available, while remote scans are 10x+ slower even in the best case and unboundedly slower in common failure modes. Local execution is also the only path to stable, replayable snapshots, which Alephgrid needs for trustworthy agent "answer receipts."

### Cited Findings
- **DuckDB is the fastest single-node analytical engine on the standard benchmark.** DuckDB v1.4 LTS took #1 on ClickBench in in-memory mode ("the fastest system on ClickBench"), and in disk-based mode handled a dataset equivalent to ~100 TB of CSV (~27 TB DuckDB database) on one machine with 12 local NVMe SSDs — [DuckDB: Benchmark Results for DuckDB v1.4 LTS](https://duckdb.org/2025/10/09/benchmark-results-14-lts.html). A MotherDuck summary frames it slightly more narrowly: #1 among open-source systems on hot runs, trailing only Umbra, a closed-source research prototype — [MotherDuck: Fastest OLAP databases compared](https://motherduck.com/learn/fastest-olap-databases-compared/). Either reading supports the same conclusion: once data is local, nothing beats this engine class.
- **Native DuckDB storage is roughly 10x faster than scanning the same data live from Postgres, per DuckDB's own measurements.** On TPC-H SF1, native DuckDB ran Q1 in 0.03 s vs 0.74 s through the postgres scanner vs 1.12 s in Postgres itself; the post states native DuckDB is ~10x faster than the scanner overall and explicitly recommends copying data into DuckDB "when queries repeat," proposing incremental caching of append-only tables — [DuckDB blog: Querying Postgres Tables Directly From DuckDB](https://duckdb.org/2022/09/30/postgres-scanner.html). (Caveat: 2022 numbers, DuckDB 0.5.1; the gap direction has not reversed since, but exact ratios will have changed.)
- **The db-benchmark (H2O.ai database-like ops) line of results shows the same thing for groupby/join workloads**: DuckDB has been a top performer since 2023, credited to improved grouped aggregation and out-of-core hash joins — [DuckDB: The Return of the H2O.ai Database-like Ops Benchmark](https://duckdb.org/2023/04/14/h2oai); current report maintained at [duckdblabs.github.io/db-benchmark](https://github.com/duckdblabs/db-benchmark/issues/13).
- **Isolation from production OLTP**: running analytical scans against a live Postgres requires the source to hold a read-only transaction/snapshot open across parallel connections for consistency (`pg_export_snapshot()` across multiple scan connections) — [DuckDB postgres scanner blog](https://duckdb.org/2022/09/30/postgres-scanner.html). Every interactive grid repaint hitting prod this way is load the DBA did not budget for; a nightly/incremental sync is.
- **"No spinners" is the first ideal of local-first software**: the Ink & Switch essay puts instant responsiveness (work at your fingertips, no round-trip waits) first among its seven ideals, with offline operation and longevity among the others — [Ink & Switch: Local-first software](https://www.inkandswitch.com/local-first/). Alephgrid's self-hosted single-binary story is a direct descendant of this argument: the workbook must open, scroll, and recompute without a healthy upstream connection.

### Inferences
- Latency arithmetic (inference from physics, not a cited benchmark): a grid viewport repaint or formula recompute needs ~tens of milliseconds to feel instant. A local NVMe columnar scan of a cached workbook table is microseconds-to-low-milliseconds; any remote query is floor-bounded by network RTT (1–40+ ms before any work happens) plus the source's own planning/execution, plus row-protocol serialization. Worse, remote latency has a *fat tail* (source under load, connection pool exhaustion, VPN flaps). A spreadsheet cannot amortize that tail: the user scrolls 20 times a minute. Federation can sometimes match local median latency; it can never match local *p99*, and p99 is what interactivity is made of.
- Reproducibility inference: an agent answer receipt is only auditable if the exact bytes it computed over can be replayed. A live federated query is computed against a remote state that no longer exists one second later and that Alephgrid cannot checkpoint. A local ingested revision (DuckDB file / Parquet / DuckLake snapshot) is a stable, hashable artifact. This is not a performance argument — it is a correctness argument for the "mediator with receipts" product thesis, and federation has no answer to it short of asking every source to support time travel.
- Spreadsheet-specific inference: formula recompute is a dependency cascade — one cell edit may trigger hundreds of small queries/aggregations. Pushing a cascade of hundreds of sub-queries over the wire per keystroke is architecturally absurd; every serious spreadsheet engine computes against memory/local storage.

### Gaps
- I found no published head-to-head benchmark of "DuckDB-local vs DuckDB-federated-over-postgres" on recent (1.3/1.4) versions; the 10x figure is from the 2022 announcement post. The directional claim is safe; the exact multiplier is not current.
- No formal HCI citation for the specific "sub-100 ms for direct manipulation" threshold was gathered in this pass (classic Card/Nielsen numbers exist but were not fetched here).

## What documented failure modes make live-connect the "worst of both worlds"?

### Takeaway
The federation story quietly depends on predicate/projection pushdown working, and in DuckDB's own scanner extensions pushdown is partial, sometimes off by default, and documented to fail silently — in which case the engine pulls the whole remote table per query anyway. That is ingest cost paid on every interaction, with none of ingest's benefits.

### Cited Findings
- **Filter pushdown was shipped off by default** in the DuckDB postgres scanner (`filter_pushdown` defaults to `false`), with only projection pushdown always on — [DuckDB postgres scanner blog](https://duckdb.org/2022/09/30/postgres-scanner.html).
- **Pushdown fails silently in practice**: a duckdb-postgres issue reports a filtered query taking 10+ seconds via full remote scan while the same predicate through raw `postgres_query` returned in milliseconds; the reporter traced ~50x slowdown to the `pg_use_ctid_scan` scan-strategy setting — [duckdb-postgres issue #369](https://github.com/duckdb/duckdb-postgres/issues/369). An earlier issue reports time-range predicates not pushed at all, making the table "impractical" to query remotely — [postgres_scanner issue #162](https://github.com/duckdb/postgres_scanner/issues/162).
- **When an operation can't be pushed down, it runs on the DuckDB side, transferring more data than needed, and the extension is slower than the same data in DuckDB native format** — [MotherDuck: PostgreSQL and DuckDB options](https://motherduck.com/blog/postgres-duckdb-options/).
- **Pushdown capability varies per connector and per build**: Yugabyte's integration gates it behind an experimental flag (`pg_experimental_filter_pushdown`) — [DuckDB on YugabyteDB](https://dev.to/yugabyte/duckdb-on-yugabytedb-31l); a third-party MSSQL extension documents its own distinct pushdown rules (e.g., ORDER BY pushdown off by default) — [hugr-lab mssql-extension docs](https://hugr-lab.github.io/mssql-extension/reading/queries/). Nothing resembling the uniform semantics a product can promise users.
- **Even DuckDB's import guide treats the scanners as ingestion tools**: when a scanner exists for a source system, it is the preferred way to *import* that data (vs CSV round-trips) — [DuckDB performance guide: import](https://duckdb.org/docs/lts/guides/performance/import). I.e., the official framing of these extensions' sweet spot is load-path, which is exactly the ingest-first architecture.

### Inferences
- For Alephgrid specifically, silent pushdown failure is catastrophic, not merely slow: the agent builds a formula, the grid re-evaluates it on scroll, and each evaluation re-pulls a multi-GB table through a row protocol. The user experiences a hung spreadsheet; the DBA experiences a rogue sequential scan every few seconds. Ingest-first pays that transfer cost once, on a schedule, with backpressure and retry logic.
- Federation also multiplies the correctness surface: per-source type mapping, collation, timezone, NULL semantics, and transaction isolation must all be handled *per query* rather than once at ingest boundary where they can be validated, coerced, and recorded in the dataset's schema contract.

### Gaps
- Issues #369/#162 are point reports and may be fixed in specific releases; I did not find official DuckDB docs enumerating exactly which operators push down in current duckdb-postgres/duckdb-mysql versions (the stable docs URLs redirect and the content wasn't retrievable in this pass). The honest claim is "pushdown is partial, connector-specific, and has documented silent-failure modes," not "pushdown is broken."
- No MySQL-specific slow-scan report was found; evidence there is indirect.

## Which real products validate copy-then-query as the dominant pattern?

### Takeaway
The products closest to Alephgrid's shape — big-data spreadsheets and DuckDB-powered dashboards — ingest rather than federate, and an entire ecosystem (dlt, Sling, Airbyte) exists because copy-then-query is the dominant analytics pattern.

### Cited Findings
- **Rill ingests into embedded DuckDB by default**: "Rill includes DuckDB as an embedded OLAP engine that ingests data from data sources and powers your dashboards" — [Rill docs: DuckDB OLAP connector](https://docs.rilldata.com/developers/build/connectors/olap/duckdb). Notably, Rill supports ATTACHing an external database via `init_sql`, and its docs say that path is *not recommended for production* — i.e., a company that could have shipped federation-first shipped ingest-first and warns against live-attach. For data too big to ingest into DuckDB they point to a bigger OLAP engine (ClickHouse), not to federation — [Rill docs: connectors](https://docs.rilldata.com/developers/build/connectors); [Rill blog: fast DuckDB-powered dashboards](https://www.rilldata.com/blog/fast-duckdb-powered-dashboards).
- **dlt** ships a first-class DuckDB destination with `write_disposition="merge"`, primary keys, and `dlt.sources.incremental("updated_at")` cursors; watermark state is stored in the destination (`_dlt_pipeline_state`), and the cursor only advances on successful load so crashes don't skip rows — [dlt SQL database tutorial](https://dlthub.com/docs/tutorial/sql-database); [Kestra dlt incremental blueprint](https://kestra.io/blueprints/dlt-incremental-sql-sync).
- **Sling** does incremental database-to-database replication where the checkpoint is simply `MAX(update_key)` queried from the target table ("the target table is the state"), with upsert semantics and backfill mode for date ranges — [Sling replication docs](https://docs.slingdata.io/sling-cli/run/configuration/replication); [Sling upserts](https://slingdata.io/articles/sling-upserts/). This is directly implementable inside Alephgrid's Rust core: the watermark pattern requires no external state service.
- **DuckLake** gives the ingest-first endgame: table data as Parquet, metadata in a SQL catalog (DuckDB/Postgres/SQLite/MySQL), ACID transactions, a snapshot per transaction, time-travel queries, and snapshot expiry management (`ducklake_snapshots`, `ducklake_expire_snapshots`) — [DuckDB docs: DuckLake extension](https://duckdb.org/docs/lts/core_extensions/ducklake). Versioned shared storage with time travel is precisely the substrate stable agent-answer receipts need.
- **Local-first as product philosophy**: the Ink & Switch essay argues no cloud-dependent architecture satisfies responsiveness, offline operation, and longevity simultaneously — [Ink & Switch: Local-first software](https://www.inkandswitch.com/local-first/). (Honesty note: co-author Adam Wiggins later said the seven ideals "aren't really a good definition of what local-first is" — the essay is a design compass, not scripture — [PowerSync: local-first origins and evolution](https://www.powersync.com/blog/local-first-software-origins-and-evolution).)

### Inferences
- The counterfactual test: if live-connect were viable for interactive analytical UIs, the ELT ecosystem (dlt/Sling/Airbyte/Fivetran) would be a niche; instead it is the backbone of the modern data stack. The market has run this experiment at scale for a decade and chose copy-then-query everywhere interactivity or reliability matters.

### Gaps
- I did not retrieve Airbyte-specific documentation in this pass; its inclusion rests on general knowledge of the ecosystem and should be cited directly if used in the final report.

## What are the honest weaknesses, the strongest federation-side objections, and the rebuttals?

### Takeaway
The federation side has four real objections — staleness, duplication/sync complexity, large-source impracticality, and compliance — and two of them (50 TB warehouses, strict data residency) are genuinely out of scope for ingest-first. The rest are engineering problems with known, citable solutions, and several "objections" are actually worse under federation.

### Cited Findings (objections and the evidence behind rebuttals)
- **Objection 1 — Staleness: "ingested data is a lie about the present."** Concede the fact; rebut the framing. Live queries give freshness but destroy reproducibility: two identical agent questions seconds apart can return different answers with no replayable artifact. Mitigation is scheduled/triggered incremental refresh with watermarks (cursor state in the destination, advancing only on success — [Kestra dlt blueprint](https://kestra.io/blueprints/dlt-incremental-sql-sync); `MAX(update_key)` checkpointing — [Sling docs](https://docs.slingdata.io/sling-cli/run/configuration/replication)) plus surfacing `last_synced_at` / TTL in the UI and in every agent answer receipt. A receipt saying "computed on snapshot S at 14:02, source watermark 13:58" is more trustworthy than a live answer with no snapshot at all. Where sub-minute freshness is a hard requirement (ops dashboards on streaming data), ingest-first genuinely loses — concede and scope it out.
- **Objection 2 — Sync pipelines are a product unto themselves: schema drift, incremental keys, deletes, backfills.** Partially concede: hard deletes without CDC are invisible to watermark-based sync, and `updated_at` cursors miss rows updated without touching the cursor column (both are inherent to the pattern the dlt/Sling docs describe — [dlt SQL database tutorial](https://dlthub.com/docs/tutorial/sql-database)). Rebuttals: (a) Alephgrid does not need to build Fivetran — scoped ingest of *named datasets* (a table, a column selection, a SQL query result) is the spreadsheet-sized unit of sync, and periodic full refresh of a scoped dataset sidesteps deletes/drift entirely at spreadsheet scale; (b) the ecosystem has commoditized the hard parts (dlt is an embeddable Python library; Sling is a single binary; the watermark pattern is ~a hundred lines in Rust); (c) federation does not escape this complexity — it converts schema drift from a sync-time error you can catch, quarantine, and alert on into a query-time error that breaks a user's open workbook.
- **Objection 3 — "You can't copy a 50 TB warehouse."** Concede fully — and then bound it. The relevant quantity is not source size but *working-set size per workbook*: a scoped SELECT of the columns and rows a workbook actually uses. DuckDB v1.4 handled a 27 TB database on one machine — [DuckDB v1.4 benchmark post](https://duckdb.org/2025/10/09/benchmark-results-14-lts.html) — so single-node capacity is far above any plausible workbook working set. For true warehouse-scale exploration, the right escape hatch is "run the aggregation in the warehouse, ingest the *result*" (a one-shot import pipeline, still ingest-first), not live federation of the grid. Note Rill's escape hatch for too-big-for-DuckDB is likewise a different OLAP engine, not federation — [Rill connectors docs](https://docs.rilldata.com/developers/build/connectors).
- **Objection 4 — Compliance/data residency: copying regulated data multiplies the audit surface.** Concede the strict-residency case: where policy forbids data at rest outside the source system, ingest-first is disqualified for those sources. Counterweights: Alephgrid is *self-hosted* — the copy stays inside the customer's own perimeter, which is categorically different from a SaaS vendor copying data out; scoped/column-level ingest means you copy the minimum; and a governed local copy with snapshot lineage is auditable in a way ad-hoc live queries from an agent are not. Also note the federation side carries its own compliance cost: long-lived privileged credentials to prod databases held by an agent-driven query engine.
- **Objection 5 — "DuckDB scanners/federation keep improving; you're betting against the roadmap."** Partially concede: pushdown has improved since 2022 and will continue to. Rebut: the floor is physics (RTT × query cascade), not implementation; and DuckDB's own ecosystem direction (DuckLake, native file formats, the import guide treating scanners as load paths — [DuckDB import guide](https://duckdb.org/docs/lts/guides/performance/import)) shows the vendor itself investing in the local-storage story as the performance tier.

### Inferences
- The objections sort cleanly: staleness and sync complexity are *costs* (payable, boundable, visible in the product as freshness metadata); scale and residency are *constraints* (define the market edge). An honest ingest-first position prices the costs and respects the constraints rather than denying them.
- The strongest single federation argument is time-to-first-value: "connect and query in 10 seconds" demos better than "connect, wait for sync, then query." The rebuttal is architectural, not dismissive: run first-query *through* the ingest path (scoped import of the queried slice, streamed into the grid as it lands) so the demo is equally fast and every subsequent interaction is local.

### Gaps
- No public post-mortems were found quantifying sync-pipeline maintenance cost vs federation maintenance cost for comparable products; the cost comparison is reasoned, not measured.
- Compliance claims are reasoned from the self-hosted deployment model, not from a cited regulatory analysis (e.g., no GDPR/data-residency legal source was consulted).

## Under what conditions does ingest-first win or lose? (Verdict conditions)

### Takeaway
Ingest-first is the correct default for Alephgrid's actual workload — files, APIs, and mid-size operational databases feeding an interactive grid and reproducibility-critical agent work — and should be stated as such, with live-connect relegated to two explicit escape hatches (warehouse-side aggregation into an ingested result; residency-constrained sources).

### Cited Findings
- Wins: file and API sources (ingest is the *only* option — there is nothing to federate to); operational Postgres/MySQL at spreadsheet scale, where native storage is ~10x faster than scanning and DuckDB's own blog recommends copying for repeated queries — [DuckDB postgres scanner blog](https://duckdb.org/2022/09/30/postgres-scanner.html); any workload where answers must be replayable, which DuckLake's snapshot-per-transaction time travel supports natively — [DuckLake docs](https://duckdb.org/docs/lts/core_extensions/ducklake); offline/single-binary self-hosted deployment — [Ink & Switch local-first ideals](https://www.inkandswitch.com/local-first/).
- Loses: sources whose scale exceeds single-node working-set extraction (multi-TB-per-query warehouse exploration) — the honest boundary even given DuckDB's 27 TB single-node demonstration — [DuckDB v1.4 benchmark post](https://duckdb.org/2025/10/09/benchmark-results-14-lts.html); strict data-residency regimes that forbid data at rest in Alephgrid's storage; hard sub-minute freshness requirements on high-churn sources where incremental sync cadence can't keep up — [dlt/Sling incremental mechanics as the bounding pattern](https://docs.slingdata.io/sling-cli/run/configuration/replication).

### Inferences
- Falsifiable loss conditions for this position (state these in the debate to demonstrate honesty): ingest-first is wrong if (1) Alephgrid's target users turn out to be primarily warehouse-native analysts whose smallest unit of interest exceeds node capacity; (2) connector pushdown becomes reliable and uniform enough that p99 interactive latency over federation approaches local (no evidence trend suggests this — the failure modes cited above are structural); or (3) the sync maintenance burden in a small OSS team crowds out core product work — the realistic biggest risk, mitigated by embedding existing tools (dlt/Sling patterns) rather than reinventing them.
- Recommended synthesis framing: "ingest-first, not ingest-only." External connections are first-class *pipelines* with scoped datasets, watermarks, TTL-stamped freshness in answer receipts, and a one-shot "query remotely, ingest the result" escape hatch. This keeps the debate position strong while absorbing the federation side's two legitimate wins as explicit, bounded exceptions rather than as the architecture.

### Gaps
- No user-research or telemetry on Alephgrid's actual source-size distribution exists yet; the "mid-size operational DB" sweet-spot claim is an assumption about the target market, not a measured fact.
