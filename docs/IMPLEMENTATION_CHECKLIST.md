## Architecture requirements

The chosen direction is **durable workbooks with automatic, policy-managed compute**. Opening a workbook is the default action. Approved profiles and dedicated compute are advanced options, not mandatory steps for every user.

- Spaces own membership, permissions and budgets; they are not machines.
- Workbooks retain stable identities, data, revisions and pinned dependencies across runtime replacement.
- Immutable `RuntimeSpec` objects describe engine/image/package versions and required capabilities. `ComputePolicy` controls profiles, quotas and isolation. `RuntimeAllocation` describes replaceable execution capacity.
- One mutable workbook has one authoritative owner at a time. Shared nodes do not imply shared application processes across untrusted tenants.
- Keep permissions, revision validation, durable commit, migrations and audit enforcement in the core. Extensions cannot bypass them.
- Preserve a useful standalone distribution. Kubernetes is an execution provider; EKS is one deployment target. Neither JupyterHub nor a cloud service becomes a mandatory dependency.
- Lease expiry alone cannot fence direct DuckDB file writes. Never start a replacement writer without enforceable exclusivity; fail closed when ownership is uncertain.

## Testing and completion requirements for every feature

Use the existing TEST_STRATEGY and TEST_MATRIX; extend them rather than creating a second reporting system. Before coding, record each task's observable contract, invariants, normal/boundary/invalid/concurrent/failure cases and expected-result oracle. Add a failing regression test for confirmed bugs where feasible.

Each feature needs relevant unit/integration tests and a real browser journey for user-facing behavior. Use property/state-machine tests, differential or metamorphic checks, fault injection, fuzzing and performance tests where the behavior warrants them. Tests must assert values, persisted state and side effects, not merely successful responses. Tests comparing shared implementation paths need an additional independent oracle for critical correctness claims.

Use deterministic seeds, isolated fixtures and observable synchronization. Record commands, versions, results, failures and gaps. Do not mask flaky tests with retries or use test counts/coverage percentages as proof of correctness. Process-kill testing is not proof of power-loss durability. Run destructive fault tests only in disposable environments.

New `N.Txx` entries are required test packages mapped to implementation IDs. Complete relevant test cases alongside each feature; do not defer all verification to the phase gate. Checked legacy entries remain historical evidence and should be rerun when affected.

## 10. Connect external data — S3 first

Depends on phase 7 permissions and phase 9 operational foundations. S3 Parquet is the first connector release. Debate update (31 October 2026): Postgres is the committed second slice after the S3 gate (10.02 promoted below); MCP follows as phase M's thin gateway; GCS, Azure, MySQL and ADBC warehouses remain deferred (12.09, 12.11) with kill criterion K1 able to pull warehouses forward. No additional connector is required for the S3 gate. Local prototypes may precede these dependencies, but do not constitute a shared-host release.

Connector-broker principles (apply to every connector, from the debate verdict and the Metabase CVE record — the connection definition is the most dangerous input a mediator accepts):
- Connections are server-side records built from structured, per-driver allowlisted fields; never raw URIs or free-form parameter maps.
- Secrets are held server-side, encrypted at rest, never present in any API response, SQL text, URL, log or export; clients and agents reference connections by opaque ID only.
- Engine secrets are created per-session in memory, never persisted where `duckdb_secrets()` could expose them.
- Remote attachment defaults to read-only; writes are a separate, explicitly granted and audited capability.
- User-supplied hosts get SSRF controls: reject private/link-local/metadata address ranges, pin DNS at connect time.
- Community (non-core-signed) engine extensions stay disabled on servers executing user SQL; any exception runs behind a worker-process boundary.
- Interactive surfaces never read a remote scan: remote query results are materialized into revision-stamped local storage with freshness records ({source snapshot token, fetched_at, watermark}), and the grid, formulas and agents read the materialization.

## M. MCP and agent access — committed thin slice after S3

Reprioritized again 1 November 2026 by the project owner: the local-workbook slice ships before S3, in launch v1 (L.04). Tools, receipts and scopes are defined over workbook data first; S3 and later connectors join the same tool surface without changing it. The text below records the earlier ordering.

Reprioritized 31 October 2026 by the debate verdict: a thin, read-only agent gateway is committed work landing after the S3 gate (10.07) and the phase 7 gate (7.12), not an open prioritization question. The empty open-source AI-native-spreadsheet niche (Quadratic closed-sourced March 2026) makes this the differentiator; the dependency order (receipts pin materialized artifacts, so materialization precedes the gateway) sets its position, not its importance. UI, CLI/SDK and MCP call the same shared application services with identical authorization, revisions, jobs and quotas; no private MCP path. If capacity halves, this phase is the first cut — nothing upstream depends on it.

Design constraints from the research (see report addendum): freeze the tool-surface contract early so later connectors are invisible to agents (same tools, same receipts); three-tier tool surface (metric/verified queries → constrained SQL over governed views → raw SQL as audited escape hatch — dbt measured 98–100% metric-tier accuracy vs 84–90% text-to-SQL); schema cards carry 3–5 sample values per column (measured ~+7 points SQL accuracy) and are served through a search tool, never preloaded; results return ~100-row preview + total count + truncation flag + opaque handle, with fetch/aggregate/sample follow-up tools reading a snapshot-pinned artifact; error messages carry recovery hints to cut agent retry loops.

- [ ] **M.01** Define a small analytical tool surface: workbook/dataset discovery, schema/profile/preview, explain/run query, bounded result pages, saved analysis and job status/cancel; validate schemas and actionable errors.
- [ ] **M.02** Expose metadata/documentation/result references as resources where useful, with essential discovery also available through tools. Return typed bounded data, explicit truncation, exact/approximate/sample labels, source revisions and workbook links.
- [ ] **M.03** Support authenticated remote Streamable HTTP and local stdio using maintained SDKs compatible with the selected protocol versions. Test ChatGPT and other chosen clients; verify current plan, transport and capability support rather than promising universal compatibility.
- [ ] **M.04** Reuse durable jobs with reconnect, cancellation and expiry; negotiate Tasks support where available and provide ordinary job-tool fallback for clients without it.
- [ ] **M.05** Start read-only; enforce per-user/workspace/source scopes on every tool and result retrieval, bounded execution, credential isolation and SQL/file/network restrictions. Treat cell contents and tool-returned text as data, never authorization.
- [ ] **M.06** Add writes only through previewable, revision-aware, idempotent application operations with configured approval policy; separate edit, export, function publication and administration privileges.
- [ ] **M.07** Add Agent connections UI with setup instructions, selected resources, access level, expiration/revoke, limits and activity attribution. Explain that results sent to an external agent may enter its model provider's context.
- [ ] **M.08** Preserve inspectable agent work: saved SQL/results, source revision, function versions, author/client attribution, change review and conflicts with simultaneous human edits.
- [ ] **M.10** Implement ResultHandles and tiered answer receipts: every agent-visible result pins a persisted, content-hashed artifact (result bytes digest) plus source `data_rev`/snapshot identifiers, plan or query digest, parameters, engine/function versions, policy version, row count and truncation flags. Tier 1 (now): recompute-and-compare verification against the content hash. Tier 2 (after the DuckLake exit, 12.10): time-travel replay against pinned snapshots. Iceberg/Delta sources pin their native snapshot IDs immediately. Result pages and exports require fresh authorization; handles are bound to owner and policy, expire, and are revocable.
- [ ] **M.11** Add a verified-query store: human-approved parameterized analyses that agents can invoke by reference; responses derived from one are marked trusted in their receipt. Promoting a successful agent analysis into the store is an explicit, permissioned action. Keep the store strictly disjoint from any evaluation datasets.

- [ ] **M.09 — Gate:** A supported agent can discover, analyze and save an inspectable workbook within granted permissions; tests demonstrate bounded results, durable jobs and no authorization bypass. Publication requires a separately approved delivery priority.
